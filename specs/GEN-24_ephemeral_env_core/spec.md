# Feature Specification: Ephemeral Environment Core (Create, Populate, Teardown)

**Feature Branch**: `GEN-24_ephemeral_env_core`

**Created**: 2026-07-27

**Status**: Draft

**Input**: User description: "GEN-24 Ephemeral environment core: create, populate, teardown. Implement the core library logic for ephemeral conda environments: create a temporary environment directory, solve and install the requested packages (respecting channel config), and tear the environment down after use. This is the shared foundation for allez oneshot."

**Jira**: [GEN-24](https://anaconda.atlassian.net/browse/GEN-24) — Ephemeral environment core: create, populate, teardown (parent epic: [GEN-19](https://anaconda.atlassian.net/browse/GEN-19))

**Operating Context**: `allez` as a whole is designed to always run inside a sandbox — that isolation boundary is established externally, before `allez` (and this feature) ever runs, not by a subcommand of `allez` itself. This feature is invoked by an AI agent operating inside that externally-established sandbox, not directly by a human at a terminal. Sandbox isolation from the host system is that external boundary's responsibility, not this feature's. Any secret this feature's environment needs (for example, a private-channel auth token) is injected into that environment by the sandbox itself, such that the real secret value is never otherwise present in it. Consequently, running, downloading, or installing anything — including any code a package runs as part of its own installation — is acceptable as long as it happens inside that sandbox boundary; this feature does not need its own consent gate or execution restrictions beyond the artifact-integrity check already required by FR-011.

## Clarifications

### Session 2026-07-27

- Q: The constitution requires package artifacts to be checksum/signature-verified before install. Is that verification in scope for this feature? → A: In scope as a testable requirement (this feature MUST verify artifact integrity before install), but satisfied by relying on the underlying package-resolution/install mechanism's own built-in verification rather than this feature reimplementing verification itself.
- Q: What should happen if teardown is signaled more than once for the same environment, or before creation/install has finished? → A: Idempotent — a repeat teardown signal is a no-op; a signal received while creation/install is still running is queued and cleanup happens automatically once creation finishes (or fails), rather than erroring or interrupting the in-progress install.
- Q: Must resolving the same requested package set against the same channel configuration produce identical installed versions across separate runs (deterministic solve)? → A: No — best-effort only; resolution may pick different compatible versions across separate runs (e.g., as new releases become available). Determinism/reproducibility across runs is not a requirement for this ticket.
- Q: Must this feature emit structured tracing events (operation, package(s), duration, result) for create/install/teardown, per the constitution's Structured Observability principle? → A: Yes — in scope; this feature MUST emit those structured events itself, since it's the boundary where create/install/teardown actually happen and can carry accurate data.
- Q: Should the ephemeral environment's location be restricted to the owning user, or is the OS-default temp/cache permission acceptable? → A: Restricted — this feature MUST create the environment's location with access limited to the owning user only; no other local user can read or write it.
- Q: What is the retry policy when a package download/install fails for a transient reason (e.g., a network blip) rather than an unresolvable package? → A: No built-in retry — this feature attempts each operation once and reports failure immediately, relying on whatever retry behavior the underlying resolution/install mechanism itself provides; it does not add its own retry layer on top.

### Session 2026-07-27 (review remediation)

- Q: Given this feature is invoked by an agent already running inside a sandbox, does it need to gate or seek consent before executing anything a package runs during its own installation (e.g., a post-install script)? → A: No — see Operating Context above; the surrounding sandbox is the security boundary for arbitrary code execution, not this feature.
- Q: Must a reported failure carry more than a human-readable message? → A: Yes — every failure this feature reports (creation, install, or teardown) MUST also carry a stable, distinct category value drawn from a small fixed set, so an automated caller can branch on outcome without parsing message text.
- Q: What does a successful creation actually hand back to the caller, given the caller never supplies a name or path? → A: Enough for the caller to execute a command using the installed packages — at minimum, the environment's own resolved location — even though the caller never supplied that location itself.
- Q: If the supplied channel configuration specifies an ordering/priority among channels, or explicit allow/deny information, must this feature honor it? → A: Yes — this feature MUST respect the channel configuration exactly as given, including any ordering, priority, or allow/deny information it carries; it does not reinterpret or reorder it.
- Q: What happens if the supplied channel configuration is empty (no channels at all)? → A: Creation fails cleanly with a distinct "no channels configured" indication — the same failure-reporting requirement as any other unresolvable request — rather than silently falling back to an undocumented default. **(Superseded by the Session 2026-07-28 entry below — the team decided on a documented fallback channel instead of failing for this specific case.)**
- Q: What happens if a configured default-package override itself resolves to an empty set? → A: Treated the same as no override configured — the built-in default package set applies.
- Q: Might channel access credentials (e.g., a private-channel auth token) ever need to pass through this feature's own inputs, error messages, or structured events in plaintext? → A: No — an Anaconda auth token needed to reach private channels is assumed to already exist in this feature's own environment, injected there by the sandbox itself (see Operating Context); acquiring, managing, and applying that token to a request is a separate capability's responsibility (see Assumptions). Regardless of how that separate capability ends up working, this feature's own inputs, error messages, and structured events MUST NOT carry credential material.

### Session 2026-07-27 (second review remediation)

- Q: What must the built-in default package set actually be, for a test to check against? → A: It MUST be a fixed, non-empty, code-defined list, documented alongside this feature's own code so a test can compare an ephemeral environment's installed top-level packages against it; the specific package names are a planning-time decision, not fixed by this specification (see FR-005).
- Q: When explicit packages are requested, must their own dependencies still be installed, or only the explicitly-named packages? → A: Their dependencies are still resolved and installed as part of installing those packages; "explicit packages, not defaults/override" governs which packages form the requested set, not whether dependency resolution runs (see User Story 3, Acceptance Scenario 3).
- Q: What are the actual category values a caller can expect from FR-010's "stable, distinct category"? → A: A fixed set covering: no channels configured, an unresolvable/uninstallable package, failed artifact-integrity verification, an unwritable/inaccessible location, and a failed teardown/cleanup (see FR-010).
- Q: How does a caller distinguish structured events belonging to one ephemeral environment from another when several exist concurrently? → A: Every event for a given environment's lifecycle MUST carry the same identifying value, distinct from any other environment's (see FR-013).
- Q: Do the "no partial environment"/"fully removed" guarantees (FR-004, SC-004, SC-007) hold even when the cleanup step itself fails? → A: Those guarantees describe the intended outcome; a distinct, separately-reported cleanup failure (FR-007, FR-010) is the one documented exception to each, not a violation of them.
- Q: Does a teardown signal arriving while a previous teardown for the same environment is already queued or in progress need distinct handling from one arriving during creation? → A: No — any caller-initiated teardown signal for an environment that isn't in a brand-new, never-signaled state is either a no-op (if teardown already completed) or folded into whatever teardown attempt is already queued or in progress; it never starts a second, concurrent removal attempt (see FR-012).
- Q: By when must an orphaned ephemeral environment (left behind by an abrupt process termination) actually be reclaimed? → A: No later than the next time this feature is asked to create a new ephemeral environment for the same caller — at that point, any previously-orphaned environment MUST be detected and removed, or its removal failure reported, so orphans do not accumulate indefinitely even without an explicit trigger (see FR-008).
- Q: Which concrete platforms must this feature's location-permission and lifecycle guarantees hold on? → A: The same four the parent epic already targets — Windows amd64, macOS aarch64, Linux aarch64, and Linux amd64 (see FR-014, SC-009).

### Session 2026-07-27 (third review remediation)

- Q: Does FR-008's normal-exit case actually require cleanup, or only unexpected exit/interruption? → A: Yes, normal exit is covered too — FR-008 and its acceptance scenario now say so explicitly, not just the Assumptions section.
- Q: What does "the same caller" mean for the orphan-reclamation deadline (FR-008/SC-003) — the same OS process, the same local user, or something else? → A: The same local user account and the same `allez` installation — not the same process, since the process that orphaned an environment is, by definition, no longer around to trigger its own reclamation.
- Q: Can orphan reclamation ever remove an environment that's still actively in use by another running process? → A: No — reclamation MUST only remove environments it can determine are actually orphaned (no longer owned by any running process), never one that's still active, regardless of how that determination is made.
- Q: How does a caller signal teardown for an environment whose creation hasn't finished yet, if FR-001's reference is only returned on successful completion? → A: Requesting creation itself — not just its successful completion — yields a reference the caller can use to signal teardown at any point, including before creation finishes.
- Q: If a caller retries a creation request after an uncertain outcome (e.g., it couldn't tell whether a prior attempt succeeded), does this feature detect and dedupe against that prior attempt? → A: No — consistent with the one-shot model, each creation request independently produces its own new environment; a retried request is not deduplicated against a possible prior success, and any resulting duplicate is the caller's own responsibility to tear down.
- Q: Does the supplied channel configuration's package-cache-location preferences (e.g., a `pkgs_dirs`-style field, if present) need to be honored by this feature? → A: Out of scope here — this feature does not itself maintain a package-download cache (see Assumptions); whether and how such a preference is honored is deferred to whichever ticket addresses shared package-cache behavior (e.g. GEN-32).
- Q: Is FR-010's failure-category set open-ended ("at least") or closed? → A: Closed for this ticket — the exact set is fixed and exhaustive as written; a later ticket (e.g. GEN-29, for a private-channel-authentication failure) MAY add further values as an additive, non-breaking extension, matching how this project's CLI's fixed error-category set (GEN-22) is already extended.

### Session 2026-07-28 (PR review remediation)

Does that still hold? → A: No — reversed after team discussion on this ticket's own review thread. When the caller-supplied channel list is empty from the start, this feature now falls back to the built-in `defaults` channel and proceeds, rather than failing (see FR-015). This reversal is scoped narrowly: it applies only when the supplied channel list is empty to begin with. A channel list that allow/deny filtering (FR-002) empties out — including one that would have emptied out the `defaults` fallback itself — still fails with the existing "no channels configured" indication, since that outcome reflects a deliberate configuration choice, not an absent one.

Whether `allez` itself should ever transparently keep an ephemeral environment around across separate `oneshot` invocations (as opposed to the shared package/repodata cache, which already does — see Assumptions) is a distinct, legitimate product question raised during review; it is deliberately deferred, not decided, and may be revisited in a later ticket.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Get a ready-to-use environment for a requested package set (Priority: P1)

An operator — an AI agent operating inside an already-sandboxed environment (see Operating Context) — needs a working environment containing a specific set of packages, without first having to invent a name or a location for it — it just wants an environment materialized on demand from a package list, ready to run commands against.

**Why this priority**: This is the entire point of the ephemeral environment capability — every other behavior (defaults, overrides, cleanup) only matters once a caller can reliably get a usable, populated environment from a package list. Nothing else in this feature is testable without this working first.

**Independent Test**: Can be fully tested by requesting an ephemeral environment for a small, known-resolvable package list and verifying that the environment is created in a system-managed location (no caller-supplied name or path), the requested packages are actually installed and usable inside it, and no unnecessary manual setup is required beforehand.

**Acceptance Scenarios**:

1. **Given** a list of requested packages and a valid channel configuration, **When** an ephemeral environment is requested for that list, **Then** a new environment is created in a system-managed temporary/cache location (no name or path supplied by the caller), every requested package is installed and available for use inside it — honoring that configuration's channel ordering and any priority or allow/deny information it specifies — and the caller receives what it needs (at minimum, the environment's own resolved location) to execute a command using it.
2. **Given** an ephemeral environment request with an empty package list and no override configured, **When** the environment is created, **Then** the environment still comes into existence populated with the built-in default package set (see User Story 3), rather than being empty or failing.
3. **Given** a package in the requested list cannot be resolved from the configured channels, **When** the environment creation is attempted, **Then** no partially-populated environment is left behind, and the caller receives a clear indication — a human-readable message plus a stable failure category — that creation failed and why.
4. **Given** a channel configuration with no channels at all, **When** an ephemeral environment is requested, **Then** the built-in `defaults` channel is used in its place and creation proceeds as if the caller had supplied it (see FR-015) — this no longer fails outright; a channel list that ends up empty only after allow/deny filtering is applied still fails cleanly with a distinct "no channels configured" indication, and no environment is left on disk in that case.

---

### User Story 2 - Environment cleans itself up after use (Priority: P1)

An operator needs the environment to disappear completely once they're done with it — whether they finish normally or their process crashes or is killed abruptly — so that ephemeral environments never accumulate as leftover clutter or wasted disk space.

**Why this priority**: Automatic teardown is what makes these environments "ephemeral" rather than just "temporary named environments a human has to remember to delete." Without reliable cleanup, every other guarantee in this feature is undermined by leftover state accumulating over repeated use.

**Independent Test**: Can be fully tested by creating an ephemeral environment, then (a) signaling normal completion and verifying the environment's location is fully removed, and (b) separately, killing the owning process abruptly mid-use or immediately after creation and verifying the environment's location is still removed (or is reliably cleaned up on a subsequent run), independent of whether User Story 1 or 3 are involved.

**Acceptance Scenarios**:

1. **Given** an ephemeral environment that has been created and used, **When** the caller signals it is done with the environment, **Then** the environment's entire directory is removed from disk.
2. **Given** an ephemeral environment that is active, **When** the owning process exits normally without an explicit teardown signal, or exits/is killed unexpectedly (e.g. a crash or a forceful kill), **Then** the environment's directory does not persist indefinitely as orphaned state — it is removed as part of exit handling, or, failing that, is detected and removed (or its removal failure reported) no later than the next time this feature creates a new ephemeral environment for the same caller (the same local user account and `allez` installation), without ever removing an environment that is still actively owned by a running process.
3. **Given** two ephemeral environments created concurrently by separate operations, **When** either one is torn down, **Then** the other environment and its installed packages are unaffected.
4. **Given** an ephemeral environment that has already been fully torn down, **When** the caller signals teardown for it again, **Then** the repeat signal is a no-op and does not error.
5. **Given** an ephemeral environment whose creation/install is still in progress, **When** the caller signals teardown before creation finishes, **Then** the teardown request is queued and the environment is cleaned up automatically as soon as creation completes or fails — the in-progress install is not interrupted.
6. **Given** an ephemeral environment whose removal cannot complete (e.g., a file is locked or in use), **When** teardown is attempted, **Then** the caller receives a distinct failure indication for that teardown attempt — separate from a successful teardown — following the same failure-reporting convention as a creation failure.

---

### User Story 3 - Sensible packages by default, overridable when needed (Priority: P2)

An operator who doesn't specify any packages still wants a useful environment out of the box, and an operator (or their configuration) who has specific preferences needs those preferences to take effect instead of the built-in defaults.

**Why this priority**: This refines the core behavior from User Story 1 rather than introducing new mechanics — it matters for making the "no packages requested" case actually useful and for letting the feature adapt to different callers' needs, but the environment lifecycle (create/populate/teardown) must already work before default selection is meaningful.

**Independent Test**: Can be fully tested by (a) requesting an environment with no packages specified and confirming the built-in default set is installed, and (b) supplying a user-level override and confirming the overridden set is installed instead of the built-in defaults — independent of whether cleanup (User Story 2) has been exercised yet.

**Acceptance Scenarios**:

1. **Given** no explicit packages are requested and no user override is configured, **When** an ephemeral environment is created, **Then** the built-in default package set is installed.
2. **Given** a user-level override for the default package set is configured, **When** an ephemeral environment is created with no explicit packages requested, **Then** the overridden set is installed instead of the built-in defaults.
3. **Given** explicit packages are requested alongside a configured default-override, **When** the environment is created, **Then** the explicitly requested packages (and their own dependencies) are installed — the override does not additionally contribute packages when explicit packages are present, matching the same no-explicit-packages condition under which the built-in default applies (FR-005). The ticket that defines the override mechanism itself (see GEN-30) may later extend this to an additive precedence rule; until then, this replace-only behavior is the effective contract.

---

### Edge Cases

- What happens when the requested package list is empty and no default override is configured? (Built-in defaults apply — see User Story 3, Acceptance Scenario 1.)
- What happens when one or more requested packages cannot be resolved or installed from the configured channels? (Creation fails cleanly with no partially-installed environment left behind — see User Story 1, Acceptance Scenario 3.)
- What happens when the supplied channel configuration has no channels at all? (The built-in `defaults` channel is used in its place and creation proceeds — see User Story 1, Acceptance Scenario 4, FR-015. If allow/deny filtering subsequently empties the effective list anyway, creation still fails cleanly with a distinct "no channels configured" indication.)
- What happens when a configured default-package override itself resolves to an empty set? (Treated the same as no override — the built-in defaults apply — see FR-006.)
- What happens when a downloaded package artifact fails integrity verification (checksum or signature mismatch)? (Rejected before being extracted, installed, or activated; install fails with no partially-installed environment left behind, same as an unresolvable package — see FR-011.)
- What happens if the owning process exits normally without signaling teardown, or is killed abruptly? (No indefinite orphaned state, and no removal of an environment still actively owned by a running process — see User Story 2, Acceptance Scenario 2.)
- What happens if teardown is signaled more than once for the same environment, or before creation has finished? (Idempotent: a repeat signal is a no-op; a signal received mid-creation is queued and cleanup runs automatically once creation finishes or fails — see FR-012.)
- What happens if teardown itself cannot complete (e.g., a locked file)? (The caller receives a distinct failure indication for that teardown attempt — see User Story 2, Acceptance Scenario 6.)
- What happens if cleanup of a partially-installed environment (after a creation failure) itself fails? (The caller receives both the original creation failure and a distinct indication that cleanup could not fully complete — neither masks the other — see FR-010.)
- What happens if the system-managed temporary/cache location is unwritable or out of space at creation time? (Creation fails with a clear, actionable error rather than a silent partial state.)
- What happens when multiple ephemeral environments are requested at the same time (e.g., by parallel operations)? (Each gets its own isolated location — see User Story 2, Acceptance Scenario 3.)
- What happens if another local, non-privileged user account on the same machine attempts to read or write an ephemeral environment's location while it exists? (Denied — see FR-014; the location is restricted to the owning user. Platform-administrator/root-equivalent accounts are subject to whatever access the operating system's standard permission model grants them, which this feature does not override.)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST create a new ephemeral environment in a system-managed temporary/cache location without requiring the caller to supply a name or an on-disk path. Requesting creation (not only its successful completion) MUST yield the caller a reference usable to signal teardown at any point, including before creation finishes; on successful completion, that reference MUST resolve to everything the caller needs to execute a command using the environment (at minimum, its resolved location), even though the caller never supplied that location itself.
- **FR-002**: System MUST accept a list of requested packages and a channel configuration as inputs, and install the requested packages into the newly created environment using that channel configuration exactly as given — including any channel ordering, priority, or allow/deny information it specifies — without reinterpreting or reordering it. Where the chosen underlying package-resolution/install mechanism cannot represent one of the priority modes this feature's channel configuration exposes (for example, it supports only two priority modes where this feature's configuration shape supports three), this feature MUST map the unsupported mode onto the mechanism's closest available equivalent and document that mapping as an accepted, deliberate approximation — this is a final, ratified decision for such cases, not an open question, and does not itself violate this requirement's "exactly as given" intent, which governs channel *ordering and membership*, not a priority mode the selected mechanism has no way to represent at all. The one exception to "exactly as given" is an entirely absent channel list, which FR-015 covers separately.
- **FR-003**: System MUST treat channel configuration (which channels to use, plus any ordering, priority, or allow/deny information) as an input it consumes rather than something it produces — parsing user preference sources into that configuration is a separate capability this feature depends on but does not implement. This feature does not itself carry any non-secret authentication-configuration field (e.g. "which channels require authentication and how") for this ticket's scope; a future ticket (e.g. GEN-29) that adds private-channel authentication owns adding such a field additively. Each configured channel is accepted as an opaque identifier (a URL or name); this feature does not parse, validate, or reject its contents, including any embedded credentials a caller mistakenly supplies — callers MUST NOT supply a credential-bearing channel identifier to this feature. The actual secret credential value is never expected to be part of this configuration (see Assumptions), and this feature applies defense-in-depth redaction to any channel identifier it does format into a message or event, but that redaction is not an input-validation gate.
- **FR-004**: System MUST resolve and install the full requested package set atomically: if any requested package cannot be resolved or installed, environment creation fails as a whole and no partially-installed environment is left on disk. Resolution is best-effort across separate runs: because the set of package versions available from the configured channels can itself change between runs (e.g., a new release becomes available), the same requested package set and channel configuration are not required to produce identical installed versions on separate occasions; this reflects a change in an input (channel availability), not non-determinism within a single resolution attempt.
- **FR-005**: System MUST apply a built-in default package set when the caller requests no explicit packages and no override is configured. This default set MUST be fixed, non-empty, and documented alongside this feature's own code (the specific package names are a planning-time decision, not fixed by this specification).
- **FR-006**: System MUST support a user-configured override of the default package set, taking effect in place of the built-in defaults when no explicit packages are requested. An override that itself resolves to an empty set is treated the same as no override — the built-in default set applies. The mechanism by which that override is authored/supplied is defined by a separate, related capability; this feature only needs to consume the resolved override.
- **FR-007**: System MUST fully remove an ephemeral environment's directory and its installed packages when the caller signals it is done using that environment. If removal itself fails (e.g., a file is locked or in use), System MUST report that failure distinctly from a successful teardown, following the same failure-reporting requirement as FR-010; this is the one documented exception to FR-004's and FR-007's own "fully removed"/"no partial state" guarantees.
- **FR-008**: System MUST also remove an ephemeral environment's directory when the owning process exits — normally without an explicit teardown signal, or unexpectedly (e.g. a crash or a forceful kill) — or, if that immediate removal cannot happen, MUST detect and remove it (or report that its removal failed) no later than the next time this feature creates a new ephemeral environment for the same caller (the same local user account and `allez` installation), so ephemeral environments are never silently left as undetected orphaned state — every orphan is either removed, has its removal failure explicitly reported, or — if liveness itself cannot be determined at all due to a genuine I/O error accessing its liveness marker — is reported as a distinct, conservative "unknown" outcome that is never touched, never left undetected (it remains present in the reported outcomes), and never conflated with either "removed" or "removal failed." This detection MUST NOT remove an environment that is still actively owned by a running process — only ones it can determine are actually orphaned. A failed reclamation attempt MUST be reported as a distinct signal, using the same message/category shape FR-010 requires (reusing its failed teardown/cleanup category), separate from that new creation's own outcome. Reclamation's own *outcome* (success, failure, or unknown) MUST NOT block or fail the new creation that triggered it, which succeeds or fails independently on its own merits; a brief, bounded delay needed purely so a new creation and a concurrently-running reclamation scan never observe each other mid-operation is not "blocking the new creation" in the sense this requirement forbids — only letting reclamation's result determine creation's result would be.
- **FR-009**: System MUST allow multiple ephemeral environments to exist and be torn down independently and concurrently, without one environment's lifecycle affecting another's.
- **FR-010**: System MUST report creation, install, and teardown failures with both a human-readable message and a stable, distinct category value, so an automated caller can understand and branch on what failed without parsing message text, distinct from a successful outcome. For this ticket, the category MUST be drawn from exactly this fixed, exhaustive set: no channels configured, an unresolvable/uninstallable package, failed artifact-integrity verification, an unwritable/inaccessible location, and a failed teardown/cleanup. A later ticket (e.g. GEN-29, for a private-channel-authentication failure) MAY add further category values as an additive, non-breaking extension, matching how this project's CLI's fixed error-category set (GEN-22) is already extended. If cleanup of a partially-installed environment itself fails after a creation failure, the caller MUST receive both the original creation failure and a distinct indication that cleanup could not fully complete, rather than one masking the other. This feature does not implement its own retry layer for transient failures (e.g., a network blip during download): each operation is attempted once and its outcome reported, relying on whatever retry behavior the underlying package-resolution/install mechanism itself provides.
- **FR-011**: System MUST verify the integrity (checksum or signature) of every package artifact before it is extracted, installed, or activated in the environment, rejecting and failing the install if verification fails (see Assumptions for how this guarantee is satisfied). This requirement covers artifact integrity only — it is not a code-execution safety control, since code-execution safety is provided by the surrounding sandbox (see Operating Context).
- **FR-012**: System MUST treat a caller-initiated teardown signal for an environment that is not in a brand-new, never-signaled state as either a no-op (if teardown already completed) or as folded into whatever teardown attempt is already queued or in progress for that environment — it never starts a second, concurrent removal attempt. System MUST treat a caller-initiated teardown signal — distinct from the owning process exiting on its own, which FR-008 covers — received while creation/install is still in progress as queued: the in-progress creation/install MUST be allowed to finish (or fail) undisturbed, after which cleanup runs automatically without requiring the caller to re-signal.
- **FR-013**: System MUST emit a structured observability event (capturing at minimum: operation name, the effective top-level package(s) actually being installed for that environment — i.e. the explicit request, or the built-in default/override when no explicit packages were given, per FR-005/FR-006 — duration, and result/outcome) for each of the create, install, and teardown steps of an ephemeral environment's lifecycle, including failures. Every event for a given environment's lifecycle MUST carry the same identifying value, distinct from any other environment's, so concurrently-existing environments' events can be told apart. These events' shape MUST include a schema-version field, consistent with the schema-versioning convention already established elsewhere in this project's structured output. Structured events and error messages MUST NOT contain credential material, regardless of how private-channel authentication ends up being supplied to this feature.
- **FR-014**: System MUST create an ephemeral environment's location with access restricted to the owning user only, so no other local, non-privileged user account on the same machine can read or write its contents while it exists. This restriction follows each supported platform's standard permission model — Windows amd64, macOS aarch64, Linux aarch64, and Linux amd64 (the epic's own target list) — and does not attempt to override what a platform-administrator/root-equivalent account can otherwise access.
- **FR-015**: System MUST fall back to a built-in default channel (`defaults`) and proceed as if the caller had supplied it, when the caller-supplied channel list is empty from the start — rather than failing with the "no channels configured" indication for this specific case. This is the one deliberate exception to FR-002/FR-003's "consumed, never produced, never reinterpreted" framing: substituting one fixed, non-secret, built-in channel name when the input is entirely absent is the same category of decision as the built-in default package set (FR-005), not a parsed-preference-source derivation. This fallback does not apply once a non-empty channel list exists: if allow/deny filtering (FR-002) subsequently empties an otherwise non-empty list — including a list containing only the fallback channel itself — creation still fails with the existing "no channels configured" indication, since that outcome reflects a deliberate configuration choice rather than an absent one.

### Key Entities *(include if feature involves data)*

- **Ephemeral Environment**: A transient, unnamed, caller-unspecified-location environment holding a specific, fully-installed set of packages. Exists only for the duration of one operation; created on demand and torn down automatically — never intended to be reused, listed, or referenced by name across separate operations (that is the domain of path-based, persistent environments, handled elsewhere). Requesting its creation yields a reference usable to signal teardown right away; once creation succeeds, that same reference resolves to everything the caller needs (at minimum, its location) to execute a command using it.
- **Requested Package Set**: The list of packages a caller explicitly wants installed into a given ephemeral environment (their own dependencies are installed too, as part of installing them), which may be empty, in which case the effective set falls back to the built-in defaults (or their configured override) instead. Explicit packages always take precedence over the built-in defaults and any configured override — the two are not merged (see User Story 3, Acceptance Scenario 3).
- **Channel Configuration**: The resolved set of package sources (their ordering/priority and any allow/deny information) this feature is given as an input to use during installation, honored exactly as supplied; it does not derive this configuration itself, carries no authentication-related field for this ticket's scope, and never carries the secret credential value itself (see Assumptions). The one exception is an entirely absent channel list, which this feature substitutes with its own built-in `defaults` fallback rather than deriving from a parsed preference source (see FR-015).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A caller can obtain a fully installed, ready-to-use ephemeral environment for any package list resolvable from the supplied channel configuration without ever having to supply a name or a file-system path — 100% of successful creations require zero caller-supplied naming/pathing input.
- **SC-002**: 100% of ephemeral environments that reach a signaled "done" state are either fully removed from disk with no residual directory left behind, or — if removal itself fails — the caller receives a distinct failure indication for that specific teardown attempt.
- **SC-003**: Ephemeral environments left behind by normal exit without an explicit teardown signal, or a crash/forceful kill, do not accumulate as silent, undetected orphaned state — verified by cleanup either completing at exit time, or being detected and removed (or its removal failure explicitly reported, or reported as a distinct "unknown" outcome if liveness genuinely cannot be determined) no later than the next time this feature creates a new ephemeral environment for the same caller (same local user account and `allez` installation), without that reclamation attempt's own outcome ever determining the new creation's own success or failure — with zero orphaned environments that are neither removed, reported failed, nor reported unknown, and zero cases of an actively-owned environment being mistakenly removed, after a full test cycle.
- **SC-004**: When package resolution or installation fails for any requested package, the caller receives a failure indication — a human-readable message plus a stable category value — and no partially-installed environment remains on disk (or, if its cleanup itself fails, a distinct cleanup-failure indication is reported alongside the original failure), in 100% of tested failure scenarios.
- **SC-005**: Callers who configure a default-package override see that override applied instead of the built-in defaults in 100% of no-explicit-package creations.
- **SC-006**: 100% of package artifacts installed into an ephemeral environment have passed integrity verification (checksum or signature) against their own declared checksum at the time they were downloaded and verified, before being extracted, installed, or activated; zero unverified or checksum-mismatched artifacts reach an active environment across a full test cycle. This describes verification of the artifact *as downloaded* — it does not guarantee that a shared cache entry a package's own (permitted, per FR-011's Assumptions) install-time code could subsequently mutate remains unchanged forever after; that residual risk is a distinct, explicitly accepted one (see the Assumptions' cross-invocation cache note), not a violation of this criterion, which is about the verification step itself, not perpetual post-verification cache integrity.
- **SC-007**: 100% of *caller-initiated teardown signals* for a given environment are handled without starting more than one *concurrent* removal attempt and without interrupting an in-progress install: a signal is the no-op FR-012 already describes if teardown has already completed via any path (including cleanup from a creation failure); a signal is folded into whatever removal attempt is already queued or in progress via any path if one exists; otherwise, this signal is the one that starts or queues that environment's sole caller-signaled removal attempt. Exactly one of these three cases applies to every signal, so no environment's *signaled* lifecycle ever runs two removal attempts side by side; each such signal's environment ends up in the same end state SC-002 already describes (fully removed, or a distinct reported teardown failure). This is a distinct guarantee from FR-008/SC-003's own orphan-reclamation deadline: if a caller-signaled removal attempt itself fails and that owning process later exits or crashes, a still-undetermined-liveness leftover directory remains subject to FR-008's separate reclamation path on a later `create()` call, which is not a second *caller-signaled* attempt and not a violation of this criterion.
- **SC-008**: Every create, install, and teardown step — including failures — produces a structured, versioned event carrying an identifier that ties it to its specific environment's lifecycle, capturing what operation ran, on which effective top-level package(s) (per FR-013), how long it took, and its outcome (including a stable category for failures), enabling an operator to reconstruct what happened — including telling concurrent environments apart — without re-running the operation.
- **SC-009**: 100% of ephemeral environment locations are created with owning-user-only access; zero cases where another local, non-privileged account can read or write an environment's contents while it exists, across a full test cycle on each of the epic's supported platforms (Windows amd64, macOS aarch64, Linux aarch64, Linux amd64).

## Assumptions

- This feature is a library capability, not a standalone user-facing command; the observable behaviors above are exercised directly (e.g., via tests/an internal API) rather than necessarily through a finished CLI subcommand — wiring this capability into `allez oneshot`'s CLI surface is a separate, sibling ticket.
- This feature runs inside an already-sandboxed environment on behalf of an AI agent, not a human operator (see Operating Context). Code execution safety for anything a package runs during its own installation is the surrounding sandbox's responsibility, not this feature's; this feature's own responsibility is limited to artifact-integrity verification (FR-011).
- Channel configuration (which channels to use, and any non-secret access configuration for private ones) is produced by a separate capability and supplied to this feature as a ready-to-use input; this feature does not read or parse `~/.condarc` itself, and does not implement private-channel authentication.
- Credential material needed to reach private channels (e.g., an Anaconda auth token) is assumed to already exist in this feature's own environment, injected there by the sandbox itself (see Operating Context) — this feature does not create, manage, or acquire it. Acquiring the token, deciding when it applies, and actually authenticating a channel request with it is a separate, related capability's responsibility (not this feature's), regardless of the exact mechanism that capability ends up using. This feature's own inputs, error messages, and structured events are never expected to carry secret values in plaintext; this feature does not itself implement authentication-related redaction (no auth-specific logic exists to redact from, since no authentication is added in this ticket — see FR-003), but it does apply a defense-in-depth safeguard to any channel identifier it formats into an error message or a structured event, purely against the possibility of a caller-supplied mistake, not because this feature expects to ever receive one.
- The mechanism for authoring/storing a default-package-set override is defined by a separate, related capability; this feature only needs to consume the effective override once resolved. Whether that mechanism's precedence between built-in defaults, an override, and explicit per-invocation packages stays replace-only or becomes additive is that capability's (GEN-30's) decision to document and test; this feature implements the replace-only rule described in User Story 3 until a later ticket revises it.
- Ephemeral environments are one-shot for the current scope: they are not cached, reused, or referenced by name across separate operations. Whether the underlying package-resolution/install mechanism maintains its own shared package-download cache across separate ephemeral environments (for performance) is not defined by this feature and is deferred to whichever ticket addresses performance (e.g. GEN-32); this feature's own guarantee is only that the ephemeral environment's directory and the packages installed into it are removed on teardown, independent of any such underlying shared cache. **Explicit, ratified product decision**: that shared cache deliberately persists across separate `allez` invocations, not just within one; a compromised package's own code (execution permitted, per FR-011's Assumptions and Constitution X's clarification) writing to it during one sandboxed invocation and a later, separate invocation reading that result back is an accepted risk, not an open question for a later planning artifact to reopen.
- **Provisional, not permanent** (raised during review, see Session 2026-07-28): this one-shot behavior is this ticket's own scope, not a closed product decision — the parent epic itself only commits to it "for now." A caller-visible reuse mechanism for a populated environment already exists at the path-based `create`/`run` layer (GEN-26/GEN-27); whether `allez` should ever also let a caller transparently reuse a still-populated *ephemeral* environment across separate `oneshot` invocations, instead of always tearing it down, is a distinct, legitimate question left for a later ticket to decide, not for this one to preempt.
- "System-managed temporary/cache location" follows whatever OS-appropriate temp/cache directory convention the runtime environment already uses — no specific directory layout is mandated by this feature's user-facing behavior.
- Concrete performance targets (e.g., how fast environment creation must be) are not defined by this feature and are tracked separately; this feature's success criteria focus on correctness and cleanup guarantees rather than speed.
- "Signals it is done" (FR-007) refers specifically to an explicit, caller-initiated teardown request. The owning process's normal exit or crash (FR-008) is a distinct case — process termination, not a caller-initiated signal — and both cases result in cleanup, whether immediate or bounded by FR-008's own reclamation deadline. This feature has no concept of a human-initiated interrupt (e.g. a terminal Ctrl-C): it is invoked by an AI agent inside a sandbox, not by a human at a keyboard, so "unexpected exit" here means a crash, an out-of-memory kill, a supervising sandbox terminating the process, or similar — never a human interactively cancelling a command.
- Artifact integrity verification (FR-011) is expected to be provided out of the box by whichever package-resolution/install mechanism is selected at planning time (leading candidates automatically verify checksums in their standard install path); this feature's job is to ensure that mechanism's verification is actually enabled/relied upon, not to build a redundant verification layer. **This is a final, ratified product decision** (see the constitution's Principle X clarification) — relying entirely on the selected mechanism's own built-in checksum behavior, exactly as that mechanism implements it, is not an open question for future review to re-raise.
- Cross-run reproducibility of resolved package versions (e.g., via a lockfile pinning exact versions) is explicitly out of scope for this ticket, consistent with the epic's own exclusion of lock files; each ephemeral environment creation resolves independently against whatever is currently available from the configured channels. This best-effort-across-runs behavior (FR-004) reflects channel availability itself changing over time, not non-determinism within a single resolution attempt.
- Retrying a failed operation (e.g., after a transient network error) is the caller's responsibility (such as an agent retrying the whole `oneshot` invocation), unless the chosen underlying package-resolution/install mechanism already retries transient errors on its own; this feature does not add a bespoke retry layer. Retrying a creation request after an uncertain outcome (e.g., the caller couldn't tell whether a prior attempt succeeded) is not deduplicated against a possible prior success — consistent with the one-shot model, each request independently produces its own new environment, and any resulting duplicate is the caller's own responsibility to tear down. **This is a final, ratified product decision, not a Constitution IX gap** (see the constitution's Principle IX clarification): a new ephemeral-creation request is a new operation, not a retry of a completed one.
- "The same caller," used by FR-008's/SC-003's orphan-reclamation deadline, means the same local user account on the same `allez` installation — not the same process, since the process that orphaned an environment is, by definition, no longer running to trigger its own reclamation.
- Whether the supplied channel configuration carries a package-cache-location preference is not addressed by this feature: this feature does not itself maintain a package-download cache (see the shared-cache Assumption above), so honoring such a preference, if it exists, is deferred to whichever ticket addresses shared package-cache behavior (e.g. GEN-32).
- Of the epic's four installation targets, macOS support is Apple Silicon (`aarch64`) only, matching FR-014/SC-009's own target list ("macOS aarch64") — Intel/`amd64` macOS is explicitly not a supported target for this feature or the parent epic, and is not expected to be tested, built for, or made to work.
- Mapping FR-010's five failure categories to a process exit code is not this feature's concern: this feature has no CLI surface at all (see the first Assumption above) and returns only structured success/failure outcomes to its caller; deciding and documenting an exit-code scheme for those categories is whichever ticket wires this feature into a CLI (e.g. GEN-25).
