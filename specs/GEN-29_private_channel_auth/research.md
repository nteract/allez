# Phase 0 Research: Private Channel Authentication

## Decision 1 — Private-channel classification (FR-003)

A configured channel is private if and only if `.condarc`'s `channel_settings` field contains an entry whose `channel` value matches that channel's resolved URL and whose settings map contains a key named `auth` (any value; this feature does not implement conda's pluggable auth-handler system, it reuses the field's existing presence as a single binary signal: "this channel needs the token"). A channel with no matching entry is never private, regardless of its host or URL shape. There is no host-based or URL-shape-based fallback of any kind.

Matching an entry's `channel` value against a channel's resolved URL uses exact string equality after trimming a trailing `/` from both sides, or, when the entry's `channel` value ends with `/*` (a slash immediately before the star), a prefix match: the channel's URL must start with that value with the trailing `*` removed — that remainder already ends in `/`, so the matcher appends nothing further. A `channel` value ending in `*` with no slash immediately before it (for example `https://conda.anaconda.org/myorg*`) is not treated as a prefix pattern at all; it only participates in the exact-match branch above, which it can never satisfy, so it simply never matches. Conda's own documented `channel_settings` example always writes the slash before the star (`https://some.base-url-prefix/*`), so this is not a new restriction on real-world usage. Requiring the slash already present in the pattern (rather than appending one during matching) is what prevents a pattern like `https://conda.anaconda.org/myorg/*` from also matching an unrelated channel `https://conda.anaconda.org/myorg2`.

A channel that matches an entry this way receives the token regardless of its resolved URL's scheme; this feature does not restrict authenticated requests to `https`. Excluding non-`https` matches from the private set at classification time was considered and rejected: it would contradict spec.md's own trusted-input framing ("any channel an operator marks in `channel_settings` receives the token"), and every channel this feature actually targets (Anaconda-hosted, both public and private) is `https` already, so the exposure this would guard against — an operator hand-writing a private `http://` entry — has no real-world occurrence against this feature's actual target infrastructure. FR-002 attaches the credential to every request a channel needing it makes, with no scheme carve-out; this is a deliberate, stated non-goal, not a silent omission.

`allez` targets Anaconda-hosted public and private channels exclusively: both are served from the same Anaconda domains (`conda.anaconda.org`, `repo.anaconda.com`), so a channel's host carries no information about whether it is private — a customer's private org channel and a public community channel are both, structurally, `conda.anaconda.org/<name>`, distinguishable only by account entitlement on Anaconda's own servers. A design keyed on host or `channel_alias`/`default_channels` cannot express this distinction at all: every channel resolved through the same `channel_alias` would classify identically regardless of whether it is public or private, misclassifying a customer's own private channel as public whenever it shares a host with their public defaults, and misclassifying any channel on an unrecognized host as private whether or not it needs a credential. `channel_settings` is the field conda itself reserves for exactly this per-channel distinction; this codebase's own `condarc` crate already parses it into `Config.channel_settings: Option<Vec<ChannelSetting>>`, deliberately without interpreting any key (its own doc comment: the `channel` key is "a documentation convention, not source-enforced"). GEN-23's own project history assigns interpreting it to this ticket specifically (a prior PR review comment: "channel_settings isn't read at all ... it's supposed to be handled separately by GEN-29").

An operator marks a channel private by adding a `channel_settings` entry for it in their `.condarc`, alongside adding the channel itself to `channels` — the same act of "configuring a private channel" already covers both, so this satisfies FR-003's "System MUST determine which configured channel(s) need the token directly from the operator's existing `.condarc` configuration" without adding any allez-specific configuration surface.

## Decision 2 — HTTP client / header-injection mechanism (FR-001, FR-002)

A custom `reqwest_middleware::Middleware` (crate `astral-reqwest-middleware`, version `0.5.1`), not `rattler_networking::AuthenticationMiddleware`/`AuthenticationStorage`. `rattler_networking::Authentication::BearerToken` emits `Authorization: Bearer <token>` — an added scheme prefix FR-002 forbids ("forwarding the environment variable's value byte-for-byte with no modification or added scheme prefix"). A custom middleware inserts the raw string directly, gated only by the private-channel-URL match from Decision 1, and leaves every other request unmodified.

`rattler_repodata_gateway::gateway::builder::GatewayBuilder::with_client` and `rattler::install::installer::Installer::with_download_client` both accept `impl Into<LazyClient>`, and `rattler_networking::lazy_client::LazyClient` implements `From<reqwest_middleware::ClientWithMiddleware>`, confirmed against the `mamba-org/rattler` source at the commits this workspace's `Cargo.lock` pins (`rattler` 0.48.0 / `rattler_repodata_gateway` 0.31.0). `ChannelConfig`/`SourceConfig` (the only per-channel configuration `Gateway` itself exposes) carry no header or auth field; HTTP auth is documented there as the caller's own `with_client`-supplied client's responsibility, which is this feature's integration point.

Dependency versions, confirmed via `cargo tree -i reqwest --workspace` against this repository's `Cargo.lock`, already present transitively so adding them as direct dependencies pulls in nothing new:

| Crate | Version | Path used in code |
|---|---|---|
| `astral-reqwest-middleware` (package name) | `0.5.1` | `reqwest_middleware::{ClientBuilder, ClientWithMiddleware, Middleware, Next}` |
| `async-trait` | `0.1.91` | `#[async_trait::async_trait]` on the `Middleware` impl |
| `http` | `1.4.2` | `http::HeaderValue`, needed directly since `channel_auth.rs` constructs one — a crate may only reference a transitive dependency's items through a direct dependency's own re-export, not by naming the transitive crate itself |
| `reqwest` | `0.13.4` | already a direct dependency, unchanged |

`Cargo.toml` depends on the package under its published name, renamed to the import path it exposes:

```toml
reqwest-middleware = { package = "astral-reqwest-middleware", version = "0.5.1" }
async-trait = "0.1.91"
http = "1.4.2"
```

`docs.rs/astral-reqwest-middleware/0.5.1` confirms the crate's own root module is named `reqwest_middleware`, matching every code example `rattler`/`rattler_networking` themselves use internally.

`rattler_networking::AuthenticationStorage` keyed by host is rejected for the same `Bearer `-prefix reason above, and because its `CondaToken` variant embeds the token as a URL path segment (`/t/<token>/`) — a different transport than an `Authorization` header, and exactly the pattern `redact_channel_url` already exists to scrub, not what FR-002 asks for.

`reqwest` (pinned at 0.13.4) strips the `Authorization` header on a redirect whose scheme, host, or port differs from the original request, so a private channel redirecting to a different origin never leaks the token through a redirect. It does not strip the header on a same-origin redirect to a different path, so a private channel's request redirecting to a sibling path on the same host would still carry it. Every URL this feature classifies private is matched by its own literal `channel_settings` entry rather than inferred from its host, and Anaconda's own repodata/package-archive URLs are served directly rather than through same-origin path redirects in practice; this residual case is accepted rather than defended against with a custom redirect policy.

## Decision 3 — Where the classification inputs live (condarc vs. allez)

`condarc::expand_channels::ResolvedChannels` gains one new field, `channel_settings: Vec<condarc::ChannelSetting>` — a straight pass-through of `Config.channel_settings.unwrap_or_default()`, with no interpretation. `condarc` already parses this field; it was simply never threaded into `ResolvedChannels`, the type this codebase's ephemeral-environment code actually consumes. Interpreting which entries mean "this channel needs the token" (Decision 1's matching rule) lives in `allez::ephemeral::channel_auth`, not in `condarc`: "what per-channel settings did the operator write" is a generic fact about a resolved `.condarc`, squarely `condarc`'s own responsibility; "does an `auth` key in one of those settings mean allez should attach its own environment-variable token" is a decision specific to this feature, with no meaning to any other consumer of `condarc`.

`ResolvedChannels::from_channels` (the `#[non_exhaustive]`-workaround test constructor every existing ephemeral-env test already uses) defaults the new field to an empty `Vec`, meaning every test-constructed configuration classifies every channel public by construction, regardless of the channel URLs it uses. No existing call site of `from_channels` or `create_ephemeral_environment` needs to change: classification inspects only whether an entry in `channel_settings` names a given channel, never that channel's own URL shape or host, so no existing test's channel scheme (`file://`, a real `https://repo.anaconda.com` channel used by one network-gated test, or a deliberately malformed URL used by one error-path test) affects the outcome.

`condarc::ChannelSetting` (`crates/condarc/src/model.rs`) gains a derived `Eq` alongside its existing `Debug, Clone, PartialEq, Default` — a one-line addition, needed because `ResolvedChannels` itself derives `Eq` and a struct cannot derive `Eq` while holding a field, `Vec<condarc::ChannelSetting>`, whose element type does not. `BTreeMap<String, String>` (`ChannelSetting`'s own wrapped field) already satisfies `Eq`, so this adds no new constraint anywhere else in `condarc`.

## Decision 4 — Detecting HTTP 401/403 distinctly, only for a channel this feature actually authenticated (FR-005)

A shared helper, `channel_auth::reqwest_http_failure(error: &(dyn std::error::Error + 'static)) -> Option<HttpFailure>`, checks whether `error` itself downcasts to `reqwest::Error` before walking `error.source()` and downcasting each link in turn, returning the first one found as `HttpFailure { status: reqwest::StatusCode, url: Option<reqwest::Url> }` — checking the root error first, not only its sources, since either the top-level error or something further down the chain may be the `reqwest::Error` carrying the relevant status/URL, and skipping straight to `.source()` would miss the former. `reqwest::Error` exposes both `.status()` and `.url()` directly, so no `GatewayError`/`FetchRepoDataError`-specific field access is needed at either call site — this is more reliable than depending on those types' own internal shape, and `reqwest::Url` is `reqwest`'s own re-export of `url::Url`, not a new dependency.

A failure is reported as `EphemeralEnvError::ChannelAuthenticationFailed` only when `status` is 401 or 403 and `url` matches one of the private channels this invocation classified — checked with `channel_auth::matching_private_channel(url, private_channels) -> Option<&str>`, which returns the specific `private_channels` entry `url` falls under (the same request-URL-membership check `PrivateChannelAuthMiddleware::handle()` uses, there only consulted for its `Option::is_some()`; a different, later-stage check than `classify_private_channels`'s own matching of `channel_settings` patterns against configured channels). Every other outcome — no matching private channel (a public channel rejecting a request for its own, unrelated reason), or any non-401/403 failure — keeps today's existing categorization (`ResolutionFailed`/`UnresolvablePackage`/the existing hash-mismatch check) unchanged. Without this membership check, a public channel's own unrelated 401/403 would be mislabeled as an authentication failure this feature caused, even though no credential was ever attached to that request; requiring positive confirmation closes that gap.

Because membership is a precondition for constructing the variant at all, `EphemeralEnvError::ChannelAuthenticationFailed`'s payload is `channel: String`, not optional. Its value is `channel_auth::origin_only(matched)`, where `matched` is the `private_channels` entry itself: `origin_only` parses `matched` as a URL and returns only `scheme://host[:port]` (`Url::origin().ascii_serialization()`), discarding the entry's own path entirely, not merely the failing request's rattler-appended subpath (`linux-64/repodata.json`, a package filename). Dropping the whole path, not just the request-generated portion, gives this field an unconditional guarantee: no path content of any kind — operator-authored or request-generated, in a form this feature already recognizes or not — ever reaches it (Decision 6). If `matched` somehow fails to parse as a URL, or parses to a scheme (such as `file`) with no meaningful origin (not expected in either case: every `private_channels` entry is itself a member of `ResolvedChannels.channels`, already used elsewhere in `solve.rs` to construct a `rattler_conda_types::Channel`, and this feature's own classification already excludes no-host channels — Decision 1), `origin_only` returns the fixed constant `"<unparseable channel>"` rather than any part of `matched` — never a partial or best-effort rendering of the input — so the no-path-content guarantee holds unconditionally, including on this fallback path.

`install.rs`'s check needs the same `private_channels` list `solve.rs` already computed: `SolvedPackages` (the existing type `solve_packages` returns) gains a `private_channels: Vec<String>` field alongside its existing `records`/`client`, so `install_packages` can call `matching_private_channel` without recomputing classification.

Applied at both HTTP-failure sites: `solve.rs`'s `gateway.query(...).execute().await` error; `install.rs`'s `InstallerError::FailedToFetch(identifier, source)`'s existing `cause` walk (which today only checks for the literal string `"hash mismatch"`), gaining this check tried before falling through to the existing integrity/unresolvable logic.

String-matching an error's `Display` output for `"401"`/`"403"` is rejected: fragile across crate version bumps, and this codebase's own existing hash-mismatch check already sets a weaker precedent this feature should not extend.

## Decision 5 — Missing-token detection timing (FR-004)

Checked once, synchronously, at the top of `solve_packages` in `solve.rs`, before any network request is made: if Decision 1's classification finds at least one private channel among `config.channels`, and `ALLEZ_CHANNEL_TOKEN` is absent, empty, or not representable as an HTTP header value (`http::HeaderValue::from_str` rejects control characters and other non-header-safe byte sequences), return `Err(EphemeralEnvError::MissingChannelToken)` immediately — no network request is ever attempted. Treating a present-but-unusable value the same as absent keeps FR-004 to one error category rather than inventing a second one for a byte-encoding technicality; the operator's remediation is identical either way (set `ALLEZ_CHANNEL_TOKEN` to a usable value).

FR-004's Independent Test requires the error for any request to the private channel, not only after an unauthenticated request happens to fail; checking eagerly, before building the gateway/client at all, satisfies "an empty value is treated the same as an unset one" (US2 Acceptance Scenario 2) and the unusable-value case in one place.

## Decision 6 — Redaction invariant (FR-006)

The raw token value is inserted into exactly one place at runtime: an `http::HeaderValue` built once via `HeaderValue::from_str(&token)` immediately followed by `.set_sensitive(true)`, held for the lifetime of the shared client and cloned per matching request. There is no separate raw-string or `Arc<str>`/`SecretString` field retained anywhere in the design once this conversion completes — the temporary `String` `std::env::var` and `HeaderValue::from_str` themselves briefly hold is never stored beyond that one conversion.

`channels::redact_channel_url` is extended to also drop a URL's query string and fragment, in addition to its existing userinfo and `/t/<token>/` path-segment stripping, closing the gap between its current, narrower scope and FR-006's "any credential embedded in a channel URL" for the existing `UnresolvablePackage`/`IntegrityVerificationFailed` variants that already use it. `MissingChannelToken` carries no payload; there is nothing to redact beyond the fixed environment-variable name, a `&'static str` constant, in its `Display` text.

`EphemeralEnvError::ChannelAuthenticationFailed { channel: String }`'s `channel` field never carries a path at all: `channel_auth::origin_only` (Decision 4) reduces it to `scheme://host[:port]`, or to the fixed constant `"<unparseable channel>"` on its fallback path, before it ever reaches `Display`, `Debug`, or any `tracing::*!` field — no code path through `origin_only` returns any part of its input beyond the origin, so there is no path content — of any kind, recognized or not — for FR-006's redaction to need to catch. This is a stricter guarantee than `redact_channel_url`'s own path-preserving behavior, deliberately: this field can afford to drop the path entirely (the `category` field already tells an automated caller which failure this is; the origin alone is enough for a human to correlate against their own `.condarc`), where `UnresolvablePackage`/`IntegrityVerificationFailed` cannot, since those messages exist specifically to show which package or channel path failed to resolve.

Credentials embedded in a URL path segment other than the already-handled `/t/<token>/` convention (for example, arbitrary or percent-encoded credential material placed directly in a path component) are not stripped by `redact_channel_url`, which preserves path segments by design so that `UnresolvablePackage`/`IntegrityVerificationFailed` messages remain useful — removing the whole path would also remove the channel/package name those messages exist to show, and would change already-tested GEN-24 behavior. This is a pre-existing, `redact_channel_url`-wide limitation of those two existing variants, not one this feature's own new `ChannelAuthenticationFailed` field shares: that field never receives path content to begin with.

A dedicated unit test constructs a real `reqwest::Request` carrying the middleware's injected header and asserts `format!("{request:?}")` does not contain the literal token value, confirming `set_sensitive` redacts `Request`'s own `Debug` impl for this exact `reqwest`/`http` version pairing rather than relying on the upstream crate's documentation alone. A second test exercises the same assertion through the full `RUST_LOG=allez=trace` stderr path in both JSON and human log-formatter modes.

`channel_settings` entries carry keys beyond `auth` (for example `user`, per conda's own documented example) that this feature reads as part of the raw `ChannelSetting` map but never interprets or acts on; only the presence of an `auth` key participates in classification. See `contracts/channel_auth_api.md`'s Classification contract for the complete, category-level accounting of every other `condarc::Config` field this feature leaves untouched.
