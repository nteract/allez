**Created**: 2026-07-21

**Status**: Draft

## Clarifications

### Session 2026-07-21

- Q: Should this scaffold ticket establish the format-selection mechanism (flag + routing to human vs. machine-readable output) for all six stub handlers now, or defer it entirely to a later ticket? → A: Plumbing now, schema later — every subcommand gets a `--human` (or equivalent) flag and routing now; the JSON payload for stub output stays minimal/unversioned until the corresponding subcommand's real behavior is implemented in a later ticket.
- Q: What exit-code scheme should the scaffold standardize on across all six subcommands? → A: Sysexits/clap-style two-tier scheme — `0` = success (including reaching a stub handler), `2` = usage error (missing required argument, unknown subcommand/flag, missing pass-through command); finer-grained error category travels in the message/JSON body, not in additional exit codes.

### Session 2026-07-22 (post-review remediation)

- Q: `--format`/`--json` placement was inconsistent across the original planning artifacts (top-level flag in some places, after-subcommand in others, and one draft test placed it after the `--` separator). What is the single normative rule? → A: It is one global flag on the top-level `Cli`, valid either before or after the subcommand name but never after `--` (FR-013); an attempt to place it after `--` is not a parse error to trap specially — it is simply forwarded to the pass-through command like any other token, per FR-012's absolute invariant, and a dedicated test (see tasks.md) proves this. (Superseded below: `--format`/`--json` were later replaced by a single `--human` flag, which inherits this exact placement rule unchanged.)
- Q: Should the stub acknowledgment (FR-009) echo the caller's raw pass-through command/arguments in default output, given `sandbox`/`oneshot`/`run` may carry secrets after `--` (e.g. `-H "Authorization: Bearer <token>"`)? → A: No — default output redacts pass-through `program`/`args` to a non-sensitive summary (FR-016); a `--verbose`/`-v` flag reveals the full value for interactive debugging. Package names and environment paths are not redacted (not caller-supplied free-form secrets).
- Q: Is empty-string path rejection (Edge Cases) actually backed by a defined validation mechanism? → A: No, it was previously specified as required behavior with no named implementation hook. FR-015 now names one shared non-empty-path validator applied identically by `create`/`run`/`remove`.
- Q: Is the error body's `category` field (FR-011) an open string or a fixed set? → A: Fixed, closed enum for this ticket's usage-error surface (FR-017), so automated callers can match on it reliably.
- Q: Should `allez sandbox --` (the `--` separator literally present, with zero tokens after it) be treated identically to `allez sandbox` (no `--` at all) — i.e., both routing to the interactive-subshell stub path? → A: No — reviewer feedback (PR #1) flagged this as inconsistent with `oneshot`/`run`'s equivalent case, where an explicit-but-empty `--` is already a usage error: there is no plausible caller intent behind typing `--` and then supplying nothing after it. `allez sandbox --` now exits `2` with `category: missing_pass_through_command`, the same category `oneshot`/`run` already use for their own empty-`--` case (FR-017); `allez sandbox` (no `--` token anywhere in argv) is unaffected and still routes to the interactive-subshell path, exit `0` (FR-006).
- Q: Should output-format selection default to human-readable text (per the original `--format`/`--json` design) or to machine-readable JSON, and should the default ever be context-aware (e.g. TTY detection)? → A: JSON is the unconditional default; TTY detection was considered and rejected as the default-selection mechanism specifically because it cannot distinguish an agent caller from a human one — agent/coding-assistant frameworks frequently execute subprocesses through a pseudo-terminal (for color/streaming support), so `is_terminal()` would often read `true` for an automated caller, silently handing it unparseable human text. Since allez's primary audience is agents (per the epic's own framing), the design instead removes `--format`/`--json` entirely in favor of one boolean flag, `--human`, that opts *into* human-readable output; omitting it always yields JSON. This is simpler (one flag instead of an enum-plus-shorthand-plus-conflict-rule) and, per constitution Principle III, still fully compliant: format selection remains "explicit" (via `--human`), and the unconditional default is documented here rather than left to a TTY heuristic. FR-013 is revised accordingly; see contracts/cli-schema.md's Output Format Contract for the updated invocation shapes.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Discover available operations via help (Priority: P1)

A human operator or an AI agent invoking `allez` for the first time needs to discover what operations the tool supports and how to invoke each one, without consulting external documentation.

**Why this priority**: Discoverability is the entry point for every other interaction with the tool. Until help output exists and is accurate, no other subcommand can be adopted correctly by either audience (human or agent).

**Independent Test**: Can be fully tested by running `allez --help` (and `allez` with no arguments) and verifying the output lists all six subcommands with a short usage line for each — independent of whether any subcommand's own logic is implemented yet.

**Acceptance Scenarios**:

1. **Given** the `allez` tool is installed, **When** a user runs `allez --help`, **Then** the output lists all six subcommands (`oneshot`, `create`, `run`, `sandbox`, `list`, `remove`) with a one-line usage description for each.
2. **Given** the `allez` tool is installed, **When** a user runs `allez` with no arguments, **Then** the tool shows usage/help information and exits with status code `2` rather than silently doing nothing.
3. **Given** a specific subcommand, **When** a user runs `allez <subcommand> --help`, **Then** the output describes that subcommand's own required and optional arguments.

---

### User Story 2 - Invoke any subcommand with its correct arguments (Priority: P1)

An operator (human or agent) needs to invoke each of the six subcommands with the argument shapes defined for it — package lists, a target environment path, and/or a pass-through command plus its own arguments — and have the tool parse them correctly before any environment work begins.

**Why this priority**: Argument parsing and routing is the load-bearing contract every later ticket (environment creation, ephemeral runs, sandboxing) is built on top of. If parsing is wrong or inconsistent, downstream tickets inherit the defect.

**Independent Test**: Can be fully tested by invoking each of the six subcommands with a representative valid example and confirming the tool routes to that subcommand's handler with the arguments parsed as expected — no environment backend is required to verify this.

**Acceptance Scenarios**:

1. **Given** the tool is installed, **When** a user runs `allez oneshot pkg1 pkg2 -- echo hello`, **Then** the tool recognizes `pkg1` and `pkg2` as packages and `echo hello` as the pass-through command and its argument.
2. **Given** the tool is installed, **When** a user runs `allez create ./my-env pkg1 pkg2`, **Then** the tool recognizes `./my-env` as the target path and `pkg1`, `pkg2` as packages.
3. **Given** the tool is installed, **When** a user runs `allez run ./my-env -- echo hello`, **Then** the tool recognizes `./my-env` as the target path and `echo hello` as the pass-through command and its argument.
4. **Given** the tool is installed, **When** a user runs `allez sandbox -- python -c "print(1)"`, **Then** the tool recognizes the pass-through command and its arguments after `--`.
5. **Given** the tool is installed, **When** a user runs `allez sandbox` with no `--` separator at all, **Then** the tool routes to the interactive-subshell path with no additional required arguments. (See Edge Cases and FR-006 for the distinct, error-producing case of `allez sandbox --` with the separator present but nothing after it.)
6. **Given** the tool is installed, **When** a user runs `allez list`, **Then** the tool accepts the call with no positional arguments required.
7. **Given** the tool is installed, **When** a user runs `allez remove ./my-env`, **Then** the tool recognizes `./my-env` as the sole required argument and requires nothing further.

---

### User Story 3 - Get consistent, actionable errors on invalid input (Priority: P2)

An operator (especially an automation/agent caller) needs every subcommand to reject invalid or incomplete invocations the same way — with a clear message and status code `2` — so failures can be handled uniformly without special-casing each subcommand.

**Why this priority**: Consistency of failure behavior is what lets agents branch on outcomes reliably. It matters less than "does the happy path parse" (P1) but is required before this scaffold can be considered done, per the ticket's own acceptance criteria.

**Independent Test**: Can be fully tested by feeding each subcommand a representative invalid invocation (missing path, missing pass-through command, unknown subcommand) and confirming exit code `2` and a human-readable error message are produced for every case, using the same convention across subcommands.

**Acceptance Scenarios**:

1. **Given** the tool is installed, **When** a user runs `allez create` with no target path, **Then** the tool exits with status code `2` and an error message identifying the missing required argument.
2. **Given** the tool is installed, **When** a user runs `allez remove` with no path, **Then** the tool exits with status code `2` and an error message identifying the missing required argument.
3. **Given** the tool is installed, **When** a user runs an unrecognized subcommand (e.g., `allez frobnicate`), **Then** the tool exits with status code `2` and an error message indicating the subcommand is unknown.
4. **Given** the tool is installed, **When** a user runs `allez oneshot pkg1 --` with nothing after the separator, **Then** the tool exits with status code `2` and an error message indicating a pass-through command is required.
5. **Given** the tool is installed, **When** a user runs any two different invalid invocations from the above, **Then** both exit with the same status code `2` and follow the same message convention, not ad hoc per-subcommand behavior.

---

### Edge Cases

- What happens when `allez` is invoked with no subcommand at all? (Must show usage/help and exit with status code `2`, not a silent no-op.)
- What happens when `oneshot` or `run` (required pass-through command) is given `--` with nothing after it? (Usage error, exit code `2` — the pass-through command is required for these two.)
- What happens when `sandbox` (optional pass-through command) is given `--` with nothing after it? (Usage error, exit code `2`, `category: missing_pass_through_command` — same as `oneshot`/`run`'s equivalent case, per FR-006. This is distinct from omitting `--` entirely, which is NOT an error — see the next bullet.)
- What happens when `sandbox` is invoked with no `--` token anywhere in its arguments? (Routes to the interactive-subshell stub path, exit code `0`, per FR-006; NOT a usage error. `allez sandbox` and `allez sandbox --` are no longer equivalent — see FR-006 for how the two are distinguished despite sharing the same underlying pass-through-command parsing.)
- What happens when `create` or `oneshot` is invoked with zero packages listed? (See Assumptions — packages are optional; the ephemeral/target environment still resolves to a valid, if minimal, request.)
- What happens when an unrecognized flag is passed to a specific subcommand (e.g., `allez list --bogus-flag`)? (Usage error, exit code `2`, with a `category: unknown_flag` in the machine-readable body, per FR-010/FR-017.)
- What happens when subcommand names are typed with different casing (e.g., `allez List`)? (Subcommands are case-sensitive; a mismatched case is treated as unrecognized, per Acceptance Scenario 3 in User Story 3.)
- What happens when a path argument (`create`/`run`/`remove`) is an empty string? (Rejected as a missing/invalid required argument at parse time via the shared non-empty-path validator, FR-015; the tool does not check whether the path exists on disk — that belongs to later tickets that implement the actual environment operations.)
- What happens when `--human` is placed after the `--` separator (e.g. `allez sandbox -- --human`)? (Not a usage error to detect specially — per FR-012/FR-013, everything after `--` belongs to the pass-through command; `--human` in that position is simply captured as one of the pass-through command's own arguments, not parsed as an allez flag.)
- Does `--help`/`--version` output ever render as JSON? (No — per FR-013's Scope exclusion, `--help`/`--version` bypass `output.rs`'s human/JSON rendering entirely; they are always plain text regardless of `--human`/the JSON default, exactly like every other CLI tool's `--help`.)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST expose a top-level `allez` command that, when invoked with `--help` or with no arguments, lists all six subcommands (`oneshot`, `create`, `run`, `sandbox`, `list`, `remove`) with a one-line usage description for each. This output is always plain text, generated directly by the argument-parsing library, and is not subject to `--human`/JSON format selection (see FR-013's Scope exclusion).
- **FR-002**: System MUST expose per-subcommand help (e.g., `allez <subcommand> --help`) that describes that subcommand's own required and optional arguments.
- **FR-003**: `allez oneshot` MUST accept zero or more package names followed by a `--` separator and a required pass-through command (with its own arguments), and MUST reject the invocation when the pass-through command is missing (see FR-012 for the shared `--` separator invariant).
- **FR-004**: `allez create` MUST accept a required target environment path followed by zero or more package names.
- **FR-005**: `allez run` MUST accept a required target environment path followed by a `--` separator and a required pass-through command (with its own arguments) (see FR-012).
- **FR-006**: `allez sandbox` MUST accept an optional `--` separator followed by a pass-through command (with its own arguments) (see FR-012). System MUST distinguish two absent-command cases, not treat them identically: (a) no `--` token present anywhere in the invocation — System MUST route to a distinct "interactive subshell" stub path rather than treating the call as an error; (b) a literal `--` token present with zero tokens following it — System MUST reject this as a usage error (exit `2`, `category: missing_pass_through_command`, the same category `oneshot`/`run` already use for their own required-but-empty case, FR-003/FR-005/FR-017), since there is no plausible intent behind supplying the separator with nothing after it. For case (a), that stub path only acknowledges reaching the interactive-subshell code path (per FR-009's stub semantics) — it MUST NOT spawn an actual subshell; real subshell spawning is GEN-28's scope.
- **FR-007**: `allez list` MUST accept no required positional arguments.
- **FR-008**: `allez remove` MUST accept exactly one required target environment path argument and no other required arguments.
- **FR-009**: System MUST route every recognized, successfully-parsed subcommand invocation to a distinct stub handler for that subcommand, which acknowledges the parsed arguments (in the output format selected per FR-013, in the minimal normative shape defined by FR-014, with pass-through argv redacted by default per FR-016) without performing any actual environment operation (environment logic is delivered in later tickets).
- **FR-010**: System MUST reject unrecognized subcommands and malformed invocations (missing required path, missing pass-through command where required, unknown flags) before invoking any stub handler's core logic, with exit code `2` and a message that identifies what was wrong. This includes the pass-through-required check for `oneshot`/`run` (FR-003, FR-005): that check MUST run at dispatch time, before the stub handler itself is entered — not as a step inside the handler — so "reached a stub handler" (FR-009) and "was rejected as a usage error" (FR-010) remain mutually exclusive outcomes for every invocation.
- **FR-011**: System MUST apply one single, documented two-tier exit-code convention consistently across all six subcommands: exit code `0` for success (including a successfully-routed stub invocation) and exit code `2` for any usage error (missing required argument, unknown subcommand, unknown flag, missing pass-through command); finer-grained error category MUST be carried as a stable, distinct `category` field in the machine-readable error body (FR-013, FR-016) — in addition to, not instead of, the human-readable message — and MUST NOT be expressed via additional exit codes.
- **FR-012**: System MUST apply the `--` separator rule (FR-003, FR-005, FR-006) as one consistent, cross-cutting parsing invariant — not bespoke per-subcommand logic — across every subcommand that accepts a pass-through command (`oneshot`, `run`, `sandbox`), so that allez's own arguments are unambiguously distinguished from the pass-through command and its arguments the same way in all three places. This invariant is absolute: no token positioned after `--` is ever reinterpreted as an allez-level flag (including `--human`, FR-013) regardless of what that token looks like; a token that happens to be spelled identically to `--human` when placed after `--` is simply forwarded to the pass-through command verbatim, like any other pass-through argument, and this is NOT a usage error — it never triggers exit code `2` (see FR-013 for the sole valid placement window, which is strictly before `--`).
- **FR-013**: System MUST expose a `--human` flag on the top-level `allez` command that selects human-readable output for every subcommand, including stub handlers; the flag and its routing MUST exist starting with this ticket. Machine-readable JSON is the unconditional default when `--human` is omitted — there is no `--format`/`--json` flag and no context-aware (e.g. TTY-based) default-selection mechanism; JSON-by-default was chosen over TTY detection specifically because a caller's terminal-attachment state cannot reliably distinguish an automated/agent caller from a human one (agent frameworks frequently execute subprocesses through a pseudo-terminal for unrelated reasons — color/streaming support — which would otherwise cause an automated caller to silently receive unparseable human text). **Scope exclusion**: this "every subcommand, including stub handlers" scope refers to each subcommand's own success/error acknowledgment payload (rendered via `output.rs`, per FR-014/FR-016) — it does NOT extend to `--help` or `--version` output (FR-001, FR-002, FR-018), which clap generates and prints directly, bypassing `output.rs` entirely; that text is always plain, regardless of `--human`/default-JSON, exactly like every other CLI tool's `--help`. **Placement**: `--human` is a single flag defined once on the top-level `Cli` and marked global, so it MAY appear either before the subcommand name (`allez --human list`) or after the subcommand name but before any `--` separator (`allez list --human`, `allez oneshot pkg1 --human -- echo hi`); per FR-012, it MUST NOT appear after `--` — a token after `--` is always part of the pass-through command, never an allez flag, in both placement windows identically. The machine-readable (default) payload MUST include a `schema_version` field (e.g. `"0.1.0-unstable"`) so it is formally documented and versioned per the constitution's dual-primary interface principle from this ticket onward; the payload's other fields MAY stay minimal until the corresponding subcommand's real behavior is implemented in a later ticket, at which point a stable (non-"-unstable") schema version is committed. See FR-014 (minimum normative payload shape) and FR-015 (pass-through argv redaction) for what "minimal" means in practice for this ticket.
- **FR-014**: The stub success payload (human and machine-readable alike) MUST, at minimum, name the subcommand reached and echo back the arguments FR-009 says it acknowledges, in a normatively fixed minimal shape: `{schema_version, subcommand, status: "stub", parsed: {...subcommand-specific fields}}` for JSON, and an equivalent one-line human-readable rendering carrying the same facts. This exists so that two independent implementations of a given stub handler produce behaviorally identical, test-comparable output, since `contracts/cli-schema.md` freezes this shape for downstream tickets to build against.
- **FR-015**: `Environment Path` arguments (`create`, `run`, `remove` — FR-004, FR-005, FR-008) MUST be rejected as a usage error (exit `2`) when empty, via one shared, named validation function applied identically across all three subcommands — not three independent per-subcommand checks — consistent with FR-012's "one consistent, cross-cutting invariant, not bespoke per-subcommand logic" pattern already established for the `--` separator.
- **FR-016**: The default (non-`--verbose`/non-debug) stub acknowledgment for `oneshot`, `run`, and `sandbox` (the three subcommands that capture a pass-through command per FR-003/005/006) MUST NOT include the pass-through command's `program` or `args` values verbatim in its default output (human or JSON), because a caller may legitimately pass secrets as pass-through arguments (e.g. `allez sandbox -- curl -H "Authorization: Bearer <token>"`) and this ticket's own stub handlers are the first place such argv would be echoed back to the caller's terminal, logs, or agent transcript. The default acknowledgment MUST instead report that a pass-through command was captured plus a non-sensitive summary (at minimum, an argument count) — e.g. `{"program": "<redacted>", "arg_count": 2}` — sufficient to prove routing succeeded without disclosing content. A `--verbose`/`-v` flag (see research.md §5, `output.rs`) MUST reveal the full, unredacted `program`/`args` in the acknowledgment for interactive debugging, satisfying the constitution's Principle III requirement that human-readable output remain "fully-featured... including verbose/trace output suitable for interactive debugging" even though the default is redacted. `Package Reference` (FR-003, FR-004) and `Environment Path` (FR-004, FR-005, FR-008) values are NOT redacted by this requirement — they are structural identifiers, not caller-supplied free-form command arguments, and redacting them would defeat FR-009's own acknowledgment purpose for no corresponding secrecy benefit.
- **FR-017**: The machine-readable error body's `category` field (FR-011) MUST be drawn from one fixed, closed enum for this ticket's usage-error surface — `missing_argument`, `unknown_subcommand`, `unknown_flag`, `missing_pass_through_command` — not an implementation-chosen ad hoc string, so that an automated caller can match on `category` reliably across all six subcommands from this ticket onward (extending the enum in a later ticket is a additive, non-breaking change; renaming or removing an existing value is not).
- **FR-018**: System MUST expose a `--version`/`-V` flag on the top-level `allez` command that prints the crate's version string and exits `0`, matching the `[--version]` synopsis element already documented in contracts/cli-schema.md's Top-Level Command section (added during `/speckit.analyze` remediation — the contract previously asserted this flag without a backing FR). Like `--help` (FR-001), this output is always plain text and is not subject to `--human`/JSON format selection (see FR-013's Scope exclusion).

### Key Entities *(include if feature involves data)*

- **Subcommand**: One of the six named operations (`oneshot`, `create`, `run`, `sandbox`, `list`, `remove`); has a name, a short usage description, and a defined set of accepted arguments.
- **Package Reference**: A package name supplied to `oneshot` or `create`; this ticket only parses and carries the name, it does not resolve or install it.
- **Environment Path**: The target location argument supplied to `create`, `run`, or `remove`; this ticket only parses and carries the path, it does not validate existence or perform filesystem operations.
- **Pass-Through Command**: The command and its own arguments captured after the `--` separator for `oneshot`, `run`, and `sandbox`; this ticket only captures and carries it, it does not execute it.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A first-time user can identify all six available subcommands and their basic usage from `allez --help` alone, within 10 seconds, without consulting external documentation.
- **SC-002**: 100% of the six subcommands successfully parse a representative valid invocation (matching the usage patterns already documented in the parent epic) on the first attempt.
- **SC-003**: 100% of invalid or incomplete invocations (missing required path/pass-through command, unknown subcommand, unknown flag) exit with status code `2` and produce a distinguishable, actionable error message; 0% of such cases exit with status `0` or terminate without a message.
- **SC-004**: An automated caller can distinguish a successful stub invocation (exit `0`) from any usage error (exit `2`) using exit status alone, for all six subcommands, without parsing message text or JSON body content. This distinguishes success-vs-usage-error only; finer-grained failure classification (per FR-011) is carried in the message/`category` field, not in exit status.

## Assumptions

- The set of subcommands for this ticket is exactly the six named in the epic and ticket description (`oneshot`, `create`, `run`, `sandbox`, `list`, `remove`); no additional subcommands are introduced here, and the underlying environment/package-resolution logic (condarc parsing, ephemeral environment lifecycle, sandboxing behavior) is out of scope and deferred to the later tickets that already exist for each area (GEN-23 through GEN-30).
- `remove` is the sole removal verb (no `delete` alias), matching conda's own CLI convention as stated in the ticket description.
- Package lists for `oneshot` and `create` are optional (zero or more) at the parsing level; the epic already anticipates allez supplying default packages when none are given, so a zero-package invocation is a valid parse, not an error.
- Stub handlers for this ticket only need to acknowledge that a subcommand was reached with valid, parsed arguments (e.g., via output or logging); no actual conda/environment side effects occur until later tickets implement them.
- `allez sandbox` invoked with no `--` token at all is expected to eventually spawn an interactive subshell; for this ticket, that "no separator" branch is a distinct stub path (not an error) that only acknowledges reaching the interactive-subshell code path — it does NOT spawn an actual subshell, matching FR-006, with the actual subshell-spawning behavior implemented in GEN-28. `allez sandbox --` (separator present, nothing after) is a distinct case from this — see FR-006 — and is a usage error, not a variant of the interactive-subshell path. Distinguishing these two cases requires knowing whether a literal `--` token was present in argv, which the shared `PassThroughArgs` parsing type alone does not preserve (an empty pass-through-command parse result is identical either way) — the implementation resolves this via a raw-argv check scoped to the `sandbox` dispatch arm, not via the parsed `PassThroughArgs` value itself (see research.md §1, data-model.md's Pass-Through Command entity).
- Global conveniences such as `--help`/`-h` text generation and unknown-flag rejection are expected to come from whatever argument-parsing approach is chosen during planning; this specification defines the required user-visible behavior, not the parsing library or code structure.
- The machine-readable output schema for each subcommand's stub payload (FR-013) carries a `schema_version` field (e.g. `"0.1.0-unstable"`) from this ticket onward, so the constitution's "documented, versioned schema" requirement is satisfied by the letter even while payload content stays minimal; the fields *beyond* `schema_version` are intentionally minimal and subject to change until each subcommand's real behavior lands in its own later ticket, at which point a stable schema version is committed.
- The error body's `category` field (FR-011, FR-017) is a stable, distinct machine-readable value drawn from one fixed, closed enum (`missing_argument`, `unknown_subcommand`, `unknown_flag`, `missing_pass_through_command`) — not free-form prose, and not an implementation-chosen open string — separate from the free-text human-readable message, satisfying the constitution's requirement that errors crossing process boundaries carry a category in addition to a message.
- The stub success payload's minimal shape (FR-014) is normatively fixed at `{schema_version, subcommand, status, parsed}` for this ticket; `parsed`'s internal fields are subcommand-specific but the four outer keys are not — this is what makes `contracts/cli-schema.md`'s "downstream tickets MUST NOT change this contract's shape without a new spec" statement actually enforceable rather than aspirational.
- Pass-through command redaction (FR-016) is a default-mode-only behavior; a `--verbose`/`-v` flag exists specifically to disable it for interactive debugging, and this ticket's own integration tests exercise both modes (default-redacted and `--verbose`-unredacted) so parsing correctness for pass-through argv (including flag-like tokens, FR-012) remains fully verifiable without requiring secrets to be visible by default.
- The shared non-empty-path validator (FR-015) is a single named function reused by `create`, `run`, and `remove` — not three independent checks — consistent with how `validate_pass_through()` is already shared by `oneshot`/`run` for the pass-through-required rule.
