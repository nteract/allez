**Fourth revision note (post-third `/review-spec-plan-tasks` round)**: a sixth review pass (the same four parallel lanes) found the third revision's own fixes were real but two of them were specified only in prose against signatures/call graphs that couldn't actually carry what the prose required — not a regression, but not yet implementable as literally written either. This revision closes each:
- **`remove_prefix_dir()`'s signature corrected to actually carry an anchor**: it took a bare `path: &Path`, which cannot reference an already-open, already-verified handle no matter what the surrounding prose demanded. It now takes `(root: &VerifiedRoot, id: EnvironmentId)` — the same `VerifiedRoot` type `paths.rs`/T012 returns and `permissions.rs`/T013 and `orphan.rs`/T046 already anchor their own operations to (named explicitly for the first time in T012's own description, closing a second gap: nothing before this revision named a concrete, shared anchor type at all).
- **One function now owns the entire root-lock-held publication sequence**: an earlier draft split "create the directory" (T028 calling `permissions.rs` directly) from "acquire the root lock and publish the owner lock" (`orphan.rs`'s `publish_owner_lock()`) across two independently-callable steps — which could not actually guarantee the atomicity `research.md`'s own root-lock section requires, since nothing forced both to happen under one held lock. `publish_owner_lock()` is renamed and expanded to `publish_environment()`, which performs directory creation, `.owner.lock` creation/locking, and metadata-writing as one sequence under one root-lock hold, returning `PublishedEnvironment { owner_lock: OwnerLock }`. `orphan.rs`/T046 now explicitly depends on `permissions.rs`/T013 (calls its creation primitive) and `cleanup.rs`/T045 (routes every actual `Removed`/`RemovalFailed` outcome through `remove_prefix_dir()`, rather than being "independent" of the module whose whole purpose is being the *one* removal implementation).
- **`OwnerLock`'s lifetime is now modeled, not left implicit**: nothing previously said what kept the `OwnerLock` alive for the environment's actual lifetime — a bare local variable in the creation function's own call frame would drop (and release) it the instant that frame ended, making a live, still-installing environment look orphaned to a concurrent reclamation scan. `cleanup.rs`'s `CleanupGuard` (T045) now explicitly owns it, constructed by T028 immediately after `publish_environment()` returns and stored in the handle's own internal state (`data-model.md` gained a field for this) before any async solve/install work begins.
- **Root-lock wait is now a named, configurable timeout with a stated default (2 seconds, `ALLEZ_ROOT_LOCK_TIMEOUT_MS`-overridable)**, closing a Constitution VII gap (configurable-timeout-with-a-default is a hard requirement, not an implementation-time detail to defer); exhausting it maps to `UnwritableLocation`, the same category the secure-open check itself already uses.
- **Unix directory-creation atomicity tightened**: `mkdirat`'s own mode parameter is now required to be set directly to `0o700` (with a `process`-feature `umask` guard around the call), closing a real gap — a separate follow-up `fchmodat` call would have left a transient window where the directory existed at a broader-than-owner-only mode. `rustix`'s `process` feature was also missing from T001 entirely; `geteuid()`/`umask()` both need it for the ownership checks and atomicity guarantee this revision and the prior one require.
- **`Cargo.toml`/Complexity Tracking's unsafe-exception accounting corrected**: `plan.md` claimed exactly one isolated `unsafe` FFI site (`permissions.rs`'s ACL creation), but `paths.rs`'s root secure-open and `cleanup.rs`'s pre-removal re-verify both also need a raw Windows `CreateFileW` call on the no-follow path — three call sites sharing one exception category, not one call site. `plan.md`'s Constitution Check row and Complexity Tracking table now list all three.
- **A guaranteed-runnable fixture entry point**: T003's fixture previously only guaranteed generic `noarch` artifacts, which don't necessarily contain an invokable binary at all — leaving T017's new usability-spawn assertion (added last round) with nothing specific to actually spawn. T003 now names one fixture package as a dedicated, cross-platform-runnable probe (`python -c "import <package>"`), and T017 references it by name.
- **An automated crash-then-reclaim test, not only a manual one**: `tasks.md` claimed 100% automated spec coverage (T056) while FR-008/SC-003's actual crash-reclamation path was only exercised by T057's manual walkthrough. T040 now requires a second, automated variant: a real helper subprocess is spawned, holds `.owner.lock`, is forcibly killed, and `reclaim_orphaned_environments()` is asserted to reclaim it.
- **`DEFAULT_PACKAGES`'s contract contradiction resolved**: `contracts/ephemeral_env_api.md` fixed a literal `["python", "pip"]` constant while separately saying names were still implementation-time-confirmed against the fixture — self-contradictory. The literal value is now explicitly illustrative; T003's fixture remains the sole authority, consistent with how `tasks.md` already treated it.
- **FR-013/SC-008 event-field coverage strengthened**: T025/T031 previously asserted event presence and `environment_id` but not the `packages`/`duration_ms` fields FR-013 itself requires; both now assert them explicitly.
- **SC-007 narrowed to the caller-signaled removal attempts it actually governs**: an earlier wording read as "no environment ever gets more than one removal attempt across the whole system," which isn't quite true once FR-008's independent orphan-reclamation path is considered (a failed caller-signaled teardown followed by a later crash is legitimately a second, reclamation-driven attempt). SC-007 now scopes itself to caller-initiated signals, cross-referencing FR-008's separate guarantee rather than overlapping it.
- **`spec.md` purity regressions fixed**: this round's own earlier edits (and one pre-existing one) had let a forward-reference to `research.md` and two implementation-mechanism descriptions (a literal URL-redaction recipe, "typed `Result`s") leak into `spec.md`, which — being the first artifact `/speckit.specify` produces — must never cite files written after it, nor describe mechanism at all; both are corrected to describe only observable behavior/outcomes.

**Fifth revision note (post-fourth `/review-spec-plan-tasks` round)**: a seventh review pass introduced a new rule — the five documents written before task breakdown (`plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md`) must never cite `tasks.md` or a specific task ID, since `tasks.md` is derived from them, not the reverse — and, checking against it, found the pattern was already pervasive (not only introduced by recent rounds): dozens of `(T0XX)` citations and literal `tasks.md` mentions across all five documents. NOT created by `/speckit.plan`"), not as an authority for this plan's own content.

That same pass also found several real design/correctness bugs — some introduced by the fourth revision's own fixes above, not new regressions in older material:
- **A real use-after-drop hazard in the `CleanupGuard`/`OwnerLock` design**: the fourth revision made the handle own the `Arc<CleanupGuard>`, but the contract's own documented usage pattern (`handle.await_ready().await?`, chained on a temporary with no `let handle = ...;` binding) drops that temporary — and the guard along with it — the instant the statement ends, potentially removing the environment before the caller's own next line ever uses the resulting `ReadyEnvironment`. `ReadyEnvironment` now carries its own clone of the same `Arc<CleanupGuard>` (`data-model.md`'s new `keep_alive` field), so the guard's `Drop` cannot fire until every clone — handle's and `ReadyEnvironment`'s alike — is gone; `signal_teardown()`'s explicit path is unaffected, since it never relied on `Drop` in the first place.
- **A real semantic bug in the Unix directory-creation fix**: the fourth revision added a process-wide `umask` mutation around `mkdirat`, reasoning it might be needed to prevent a "wider" mode. That reasoning was backwards — `umask` can only *narrow* a requested mode, never widen it, so `mkdirat`'s own `0o700` argument already fully guarantees the result on its own. The `umask` mutation added a real, unnecessary cross-thread race in a multithreaded Tokio process for zero benefit; removed entirely.
- **A real infeasibility in the fixture-probe design**: the fourth revision's `python -c "import <package>"` usability probe (T003/T017) cannot work as specified — a `noarch: generic` package's own payload is not a Python interpreter, and nothing guarantees one is installed alongside it. T003 now builds the probe as real, per-platform artifacts shipping a trivial, dependency-free, self-contained entry point (`bin/fixture-probe` / `Scripts/fixture-probe.cmd`) that needs no interpreter at all.
- **A real path-injection gap**: the fallback root's `{user}` component came from `$USER`/`$LOGNAME`/`%USERNAME%` interpolated verbatim into a path string — an attacker-influenced value containing a path separator or `..` segment could turn one intended path component into several, or an escape. `{user}` is now required to be sanitized to a safe character set (or hashed) before it ever reaches the `format!` call.
- **A real observability gap**: nothing stored the effective top-level package list anywhere a teardown event (explicit signal, `Drop`, creation-failure, *or* orphan reclamation by a different, later process) could read it back for FR-013's `packages` field. The handle now stores it internally for the live-process paths; the on-disk metadata file (`{pid, created_at, environment_id, packages}` — `process_start_time` also renamed to `created_at`, since the design that needed a `sysinfo`-sourced start-time was superseded rounds ago and nothing since specified how to obtain it without that now-removed dependency) carries it for the orphan-reclaimed path.
- **Two stale dependency-listing contradictions**: `tasks.md`'s own "Foundational tasks are independent" list still included `T013` despite the fourth revision making it depend on `T012`, and its Parallel Opportunities section still called `T045`/`T046` independent despite the Dependencies section (correctly) saying `T046` depends on `T045`. Both corrected.
- **A test-flakiness gap in the new automated crash-reclaim test (T040)**: the helper subprocess could be killed before it actually acquired `.owner.lock`, producing a false pass. It now signals readiness before the test kills it.
- **A test-flakiness risk in the new event-field assertions (T025/T031)**: requiring `duration_ms` to be strictly non-zero could fail on a genuinely fast operation. Now asserts the field is present/well-formed, not that it's non-zero.
- **A version-compatibility risk left unpinned rather than guessed at**: `T001`/`research.md` had pinned `reqwest = "0.12"` without checking it against whatever `reqwest` major version this ticket's exact `rattler`/`rattler_networking` release actually requires — a real, checkable risk (`rattler_networking` has changed its own `reqwest` major-version requirement in its released history), but guessing a specific replacement version carries its own risk of being equally wrong. The version is now deliberately left for `cargo tree` to confirm at implementation time, exactly like the existing `aws-lc-rs`/`ISC` license question `research.md` already handles the same way.
- **A missing contract clause and two missing documentation entries**: `await_torn_down()`'s doc comment didn't mention its one immediate-resolution exception (a creation failure whose cleanup already resolved); `ALLEZ_ROOT_LOCK_TIMEOUT_MS` was specified in `research.md`/`tasks.md` but never surfaced in `contracts/ephemeral_env_api.md`'s own environment-variable inventory or `quickstart.md`; and `quickstart.md`'s test-isolation guidance said "one root per test binary" without accounting for `cargo test`'s default same-binary parallelism across the dozens of test functions sharing one root — all three closed.

Two items raised by this pass were deliberately **not** changed, and are recorded here rather than silently dropped: (1) a suggestion that production `DEFAULT_PACKAGES` shouldn't be authored to match a test fixture's own contents — this ticket's design already keeps the two concerns separable (the fixture is free to contain genuinely useful default packages, as `contracts/ephemeral_env_api.md`'s own `["python", "pip"]`-shaped illustration shows, and the new `fixture-probe` package introduced this round is explicitly kept separate from `DEFAULT_PACKAGES` for exactly this reason); (2) a stricter reading of the direction-of-dependency rule that would also forbid `plan.md`/`research.md`/`data-model.md`/`contracts/`/`quickstart.md` from citing *each other* — the rule as actually given only prohibits those five from citing `tasks.md`, grouping them together as one "planning phase" free to cross-reference internally, so this was not pursued further.

### Notes on This Feature's Specific Coupling

Unlike a typical multi-story feature with separable HTTP endpoints or UI screens, all three user stories here are exercised through one function, `create_ephemeral_environment`. "Independently testable" (per `spec.md`) means each story's own *acceptance scenarios* can be verified without needing the *other stories'* scenarios to also pass — not that each story has its own separate implementation surface. Build strictly in priority order (US1 → US2 → US3) as laid out above; do not attempt to parallelize implementation (as opposed to test-writing) across user-story phases.
