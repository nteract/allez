# Quickstart: Validating the CLI Scaffold

**Feature**: [spec.md](./spec.md) | **Contract**: [contracts/cli-schema.md](./contracts/cli-schema.md)

This guide validates that the scaffold satisfies the spec end-to-end, once implemented. It is a validation/run guide, not implementation code — see [tasks.md](./tasks.md) (generated by `/speckit.tasks`) for the build steps themselves.

## Prerequisites

- Rust stable toolchain installed (`rustup show` reports a stable channel).
- Run from the repository root, on the `GEN-22_cli_scaffold_routing` branch.

## Setup

```bash
cargo build
```

Expected: builds successfully with no `cargo clippy -- -D warnings` violations (constitution Quality Gates).

## Validation Scenarios

Each scenario below maps directly to an acceptance scenario in [spec.md](./spec.md). Run them against the built binary (`./target/debug/allez` or `cargo run --`).

### User Story 1 — Discoverability

```bash
cargo run -- --help
```
**Expect**: exit `0`; output lists all six subcommands (`oneshot`, `create`, `run`, `sandbox`, `list`, `remove`) with a usage line each.

```bash
cargo run --
```
**Expect**: exit `2`; usage/help shown on stderr (per FR-001, no silent no-op).

```bash
cargo run -- create --help
```
**Expect**: exit `0`; describes `create`'s own required/optional arguments.

```bash
cargo run -- oneshot --help
cargo run -- run --help
cargo run -- sandbox --help
cargo run -- list --help
cargo run -- remove --help
```
**Expect**: exit `0` for each; every one of the six subcommands (`create` above plus these five) describes its own required/optional arguments — this manual pass exercises all six, matching the Independent Test's "for each of the six" wording in [spec.md](./spec.md); the automated `T013` `rstest` case covers the same six programmatically.

### User Story 2 — Correct parsing per subcommand

```bash
cargo run -- oneshot pkg1 pkg2 -- echo hello
cargo run -- create ./my-env pkg1 pkg2
cargo run -- run ./my-env -- echo hello
cargo run -- sandbox -- python -c "print(1)"
cargo run -- sandbox
cargo run -- list
cargo run -- remove ./my-env
```
**Expect**: every invocation exits `0` and the stub handler's acknowledgment output identifies which subcommand was reached and the arguments it parsed (per FR-009), matching the shapes in [contracts/cli-schema.md](./contracts/cli-schema.md). Output is JSON by default (no flag needed — see the Output format section below for `--human`). By default, the `oneshot`/`run`/`sandbox` acknowledgments redact the pass-through command to `{program: "<redacted>", arg_count: N}` (FR-016) — packages and paths are shown as-is.

```bash
cargo run -- run ./my-env --verbose -- echo hello
```
**Expect**: exit `0`; identical to the `run` example above, except the acknowledgment reveals the full unredacted pass-through `program`/`args` (`echo`/`["hello"]`) because `--verbose`/`-v` was supplied (FR-016).

### User Story 3 — Consistent error handling

```bash
cargo run -- create
cargo run -- remove
cargo run -- frobnicate
cargo run -- oneshot pkg1 --
```
**Expect**: every invocation exits `2`, with a message on stderr identifying what was wrong, using the same convention across all four cases (FR-010, FR-011).

```bash
cargo run -- create ""
cargo run -- remove ""
cargo run -- List
cargo run -- list --bogus-flag
```
**Expect**: every invocation exits `2` with the same message convention as above — empty-string paths (FR-015), a case-mismatched subcommand name (`List` vs `list`, treated as unrecognized), and an unknown flag are all usage errors, not silently accepted.

```bash
cargo run -- sandbox --
```
**Expect**: exit `2` — this IS a usage error (`category: missing_pass_through_command`), distinct from `allez sandbox` (no `--` token at all), which stays exit `0` and routes to the interactive-subshell path. Per FR-006, as revised during PR #1 review: supplying `--` with nothing after it is no longer treated as equivalent to omitting `--` entirely.

### Output format flag (FR-013, FR-011, FR-014, FR-016, FR-017)

```bash
cargo run -- list
```
**Expect**: exit `0`; stdout is valid JSON (parseable by `serde_json::from_str` or `jq .`) matching `{schema_version, subcommand, status, parsed}` (FR-014) — no flag needed, JSON is the unconditional default (there is no `--format`/`--json` flag, and the default is not TTY-detected; see spec.md's Clarifications for why).

```bash
cargo run -- --human list
cargo run -- list --human
```
**Expect**: exit `0` for both; stdout is free-form human-readable text carrying the same facts as the JSON payload above — `--human` is a global flag, so both placements (before and after the subcommand name) are equally valid and produce identical output.

```bash
cargo run -- create
```
**Expect**: exit `2`; stderr is valid JSON matching `{schema_version, category, message}`, with `category` drawn from the fixed enum (`missing_argument`, `unknown_subcommand`, `unknown_flag`, `missing_pass_through_command` — FR-017), not folded into the message text. JSON is the default for errors too, always delivered on stderr, matching the human-readable error convention (see [contracts/cli-schema.md](./contracts/cli-schema.md#output-format-contract-fr-013-fr-014-fr-016-fr-017)).

```bash
cargo run -- oneshot pkg1 -- echo hi --human
```
**Expect**: exit `0`; `--human` here is forwarded verbatim as one of `echo`'s own arguments (because it appears after `--`), NOT parsed as an allez flag — output is the default JSON form, per FR-012's absolute invariant.
