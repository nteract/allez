# Research: CLI Scaffold and Subcommand Routing

**Feature**: [spec.md](./spec.md) | **Date**: 2026-07-21

All Technical Context unknowns were resolvable via informed defaults + external research (no open `NEEDS CLARIFICATION` markers remain). This document records the decision, rationale, and alternatives considered for each.

## 1. Argument parsing / subcommand routing: `clap` v4 (derive API)

**Decision**: Use `clap` v4.x with the `derive` feature. Top-level `Cli { #[command(subcommand)] command: Commands }`, `Commands` as a `#[derive(Subcommand)]` enum with 6 variants, using a shared `#[derive(Args)]` `PassThroughArgs` struct (tuple variants, e.g. `Sandbox(PassThroughArgs)`) to avoid duplicating the pass-through-args shape across `run`/`sandbox`. `oneshot` composes `PassThroughArgs` alongside a `packages: Vec<String>` field via `PackagesAndCommandArgs`; `create` is intentionally **not** built on either shared struct — `create` has no pass-through command at all (FR-004), so `CreateArgs` is its own independent type (`path: String`, `packages: Vec<String>`).

**Required-ness is enforced by a shared post-parse validation function, not a clap-level `required` attribute on the shared struct's field.** `PassThroughArgs`'s `program`/`args` field carries no `required = true` marking at the type level, because the same type is reused unconditionally-optional by `sandbox` — clap's `#[command(flatten)]` does not support a per-call-site override of a flattened struct's own field attributes, so marking the field `required` in the type definition would make it required everywhere the type is used, including `sandbox`, where FR-006 requires it to stay optional in the no-`--`-at-all case. Instead, a shared `validate_pass_through(&PassThroughArgs) -> Result<(), AllezError>` helper (see data-model.md) is called from **`main.rs`'s dispatch, immediately after `Cli::try_parse()` succeeds and before invoking the `oneshot`/`run` stub handler at all** — not from inside those handler bodies, so that "reached a stub handler" (FR-009) and "was rejected as a usage error" (FR-010) stay mutually exclusive for every invocation (see data-model.md's "Required-ness enforcement" and tasks.md T039 for the full rationale).

`sandbox`'s dispatch arm does **not** call `validate_pass_through()` unmodified, because FR-006 (updated during PR #1 review — see spec.md's Clarifications) now requires `sandbox` to reject `--` present with nothing after it, while still accepting `--` absent entirely — a distinction `validate_pass_through()`'s `pt.program.is_empty()` check cannot make on its own, since both cases parse to the identical empty `PassThroughArgs` value. This was confirmed empirically against `clap` 4.6.x, not left as a guess (see the former "Open verification item" below, now resolved): for a `#[arg(last = true)]` field, `ArgMatches::contains_id`, `value_source`, `index_of`, and `get_many` all report "not present" identically whether `--` was typed with nothing after it or omitted entirely — clap's match model simply does not retain "a bare `--` was seen" as observable state once matching is done. `sandbox`'s dispatch arm therefore runs its own check, only when `pt.program` is empty: a raw-argv scan (`std::env::args_os()`) for a literal `"--"` token, safe to run un-scoped because exactly one subcommand is dispatched per process invocation and none of allez's other global flags can themselves contain a `--` token. If found, it returns the same `Err(AllezError::MissingPassThroughCommand)` `validate_pass_through()` would produce for `oneshot`/`run`; if not found, dispatch proceeds to `sandbox::run()`'s interactive-subshell path exactly as before.

**Rationale**:
- `clap` is the de facto standard Rust CLI argument parser; derive API keeps subcommand definitions declarative and satisfies the constitution's "single, clear responsibility" and "explicit over implicit" principles (invalid subcommand/arg combinations become unrepresentable via the type system).
- **Pass-through capture**: `#[arg(last = true)]` on a `Vec<String>` field is the current (clap 4.6.x) derive-API idiom for "capture everything after `--`, preserving arbitrary flags/values without clap parsing them." Verified against `clap-rs/clap` official examples (`escaped-positional-derive.rs`, `git-derive.rs`).
- **Combining packages + pass-through in one subcommand** (`oneshot`): a non-`last` `Vec<String>` (`packages`) followed by a `#[arg(last = true)] Vec<String>` (`command`) in the same struct works correctly — `--` acts as the terminator that stops `packages`'s greedy consumption and hands remaining tokens to the `last`-marked field. (The builder-API-only `trailing_var_arg`/`allow_hyphen_values` methods are not exposed as derive attributes; `last = true` is the derive equivalent and is sufficient here.)
- **Exit codes**: clap v4 already exits with status code **2** for all usage errors (missing required arg, unknown subcommand, unknown flag, invalid value) and **0** for success/`--help`/`--version` — confirmed against `clap_builder/src/error/mod.rs` (`USAGE_CODE = 2`, `SUCCESS_CODE = 0`). `main.rs` uses `Cli::try_parse()` (not the auto-exiting `Cli::parse()`) specifically so that a parse-error `Result::Err` can be routed through `error.rs`'s consistent human/JSON renderer (adding the `category` field) before calling `std::process::exit(2)`, rather than letting clap print its own message and exit directly — this is what makes FR-011's consistent-message-format requirement achievable across all six subcommands' usage errors.
- **Shared struct pattern**: `#[command(flatten)]`/tuple-variant structs (`Run(RunArgs)`, `Sandbox(PassThroughArgs)`) let `run` and `sandbox` reuse one `PassThroughArgs`-shaped field definition instead of copy-pasting the `#[arg(last = true)]` field twice — satisfies the constitution's DRY principle, while the post-parse `validate_pass_through()` helper (rather than a type-level `required` attribute) keeps `run`'s required-ness and `sandbox`'s optional-ness from conflicting on the shared type. Confirmed via `clap-rs/clap`'s own `git-derive.rs` example (`StashArgs` flatten pattern).

**Alternatives considered**:
- `structopt` — predecessor to clap's derive API, now merged into clap itself; no reason to use the deprecated standalone crate.
- `pico-args` / `argh` — lighter-weight parsers, but lack clap's mature subcommand/help-generation/exit-code ecosystem and would require allez to hand-roll behavior clap already provides for free (rejected: more code to satisfy the same FRs, against the constitution's "no hardcoded values" and DRY principles).
- Hand-rolled `std::env::args()` parsing — rejected outright; reinvents a solved problem and risks inconsistent error/exit-code behavior across the 6 subcommands (directly undermines FR-011).
- Marking `PassThroughArgs`'s field `required = true` directly on the shared type, then relying on a separate, non-shared type for `sandbox` — rejected in favor of the post-parse validation function; duplicating the type would reintroduce the exact duplication the shared-struct pattern exists to avoid, and a single validation function is simpler to reason about than two near-identical types.
- Switching `PassThroughArgs`'s field from `#[arg(last = true)]` to clap's builder-only `trailing_var_arg(true)` mechanism, hoping it would preserve "a bare `--` was seen" as observable state — rejected; `trailing_var_arg` changes capture semantics (permits trailing tokens without requiring `--` at all), which conflicts with FR-012's requirement that `--` be the one unambiguous delimiter, and does not solve the underlying problem: the loss of bare-`--` presence lives in clap's match-result model itself, not in which capture attribute is used, so a builder-API rewrite would not help here either.
- Giving `sandbox` its own non-shared pass-through type (instead of a raw-argv scan) specifically so it could track separator-presence as a distinct field — rejected for this ticket; it would fragment the DRY `PassThroughArgs` capture struct across three call sites into "two share one shape, one doesn't" for a difference that is purely about *validation* policy, not *parsing* shape. The raw-argv scan keeps `PassThroughArgs` itself uniform across all three subcommands and confines the `sandbox`-specific policy to a small, separately-named check at the dispatch layer (see data-model.md's "Required-ness enforcement").

**Resolved via empirical verification against `clap` 4.6.x (see data-model.md's "Required-ness enforcement" and spec.md FR-006's updated wording, both added during PR #1 review remediation)**: `--` with literally zero tokens after it (e.g. `allez oneshot pkg1 --`) is treated as an empty `PassThroughArgs` (empty `program`, empty `args`), which `validate_pass_through()` then rejects uniformly for `oneshot`/`run` as `AllezError::MissingPassThroughCommand` (category `missing_pass_through_command`, FR-017). For `sandbox`, this same empty value now also produces a `MissingPassThroughCommand` rejection **when a literal `--` token was present in argv** — but is correctly accepted (empty, non-error, interactive-subshell path) when no `--` token was present at all (FR-006). Confirming which of these two states occurred cannot be done from the parsed `PassThroughArgs` value alone: verified against `clap` 4.6.4 that `ArgMatches::contains_id`, `value_source`, `index_of`, and `get_many` all report "not present" identically for a `#[arg(last = true)]` field whether `--` was typed with nothing after it or omitted entirely — clap's match model does not retain "a bare `--` was seen" once matching completes, for either the derive or builder API. The resolution is a raw-argv pre-scan (`std::env::args_os()`, checked for `OsStr::new("--")`, not `std::env::args()`, so non-UTF-8 pass-through argv stays representable) run only inside `sandbox`'s dispatch arm, only when `pt.program` is already empty — this is safe to run against the full, un-scoped argv precisely because exactly one subcommand is dispatched per process invocation, so within that arm any `--` found can only be `sandbox`'s own separator. This must still be locked with a failing integration test before implementation, per constitution Principle II (TDD) — the design decision itself is no longer open, but its test-verified behavior against the real compiled binary is (tasks.md T036).

## 2. Machine-readable / human-readable output split: `serde` + `serde_json`, single `--human` flag resolved once at startup, JSON-by-default

**Decision**: A top-level `--human` boolean flag on the `Cli` struct, marked `global = true` so it may appear either before or after the subcommand name — clap derive's `#[arg(global = true)]` makes a top-level flag valid at any position in the allez-owned portion of argv. There is no `--format`/`--json` flag: JSON is the unconditional default when `--human` is omitted, and `--human` is the sole, one-directional switch into human-readable mode — no enum type, no shorthand-boolean-plus-conflict-rule to reconcile, since there is exactly one flag governing exactly one setting. It is resolved once during arg parsing before dispatching to any subcommand. Per FR-012, it is never valid after `--`: `try_parse()` already stops interpreting flags once `--` is seen (clap's own separator semantics), so a `--human`-shaped token after `--` is captured by the flattened `PassThroughArgs`'s `#[arg(last = true)]` field like any other token — no special-case detection code is needed, clap's existing behavior already does the right thing here, and this is exactly what the dedicated integration test (tasks.md) locks in. Each stub handler's acknowledgment (FR-009, FR-014) is emitted as either a `serde_json::json!({...})` object (default/machine) or free-form text (`--human`) in the normatively fixed minimal shape `{schema_version, subcommand, status, parsed}` (FR-014), with `parsed`'s pass-through fields redacted by default (FR-016, see Decision 5). Error bodies always include a `category` field drawn from a fixed enum (FR-011, FR-017, see Decision 6) alongside the human-readable message.

**Rationale**: This satisfies the clarified scope (`/speckit.clarify` Q1 → Option C: "plumbing now, schema later") — the flag and its routing exist for all six subcommands starting with this ticket. Marking the flag `global = true` rather than leaving it a plain top-level-only field makes both placement styles used throughout `contracts/cli-schema.md`'s example tables ("`allez --human list`" and "`allez list --human`") simultaneously valid without contradiction — clap's own docs (`clap-rs/clap`'s `Command::arg` + `ArgAction` reference) confirm `global` args are inherited by every subcommand's own `ArgMatches`, which is exactly the "before or after the subcommand, never after `--`" rule this ticket needs. JSON-by-default (rather than human-by-default, or a TTY-detected default) was chosen during a later review pass (PR #1 discussion, see spec.md's Clarifications) specifically because `allez`'s primary audience is agents/automation (per the epic's own framing), and a caller's terminal-attachment state cannot reliably distinguish an agent caller from a human one — coding-agent/orchestration frameworks routinely execute subprocesses through a pseudo-terminal for unrelated reasons (color/streaming support to their own UI), which would make `is_terminal()`-based detection misclassify a large fraction of real agent invocations as "human," silently handing back unparseable free-form text instead of JSON. An unconditional default removes that failure mode entirely: a human at an interactive terminal pays a one-flag cost (`--human`) to get readable output; an agent that forgets to pass anything still gets a stable, parseable JSON contract by default. The `schema_version` field (added during `/speckit.analyze` remediation of finding D1) resolves an otherwise-literal conflict with constitution Principle III's unconditional "documented, versioned schema" requirement: rather than shipping a schema-less/unversioned payload and deferring the *entire* requirement, the payload is versioned (`"0.1.0-unstable"`) from day one, while its non-version fields stay intentionally minimal until real behavior exists to describe. The `category` field on error bodies similarly resolves finding F1 against Principle XI ("errors...MUST carry a stable error code/category in addition to a human-readable message") by giving that category a distinct, stable field rather than leaving it foldable into free-text message content.

**Alternatives considered**:
- Deferring the flag entirely to later tickets (clarify Option B) — rejected by the user during `/speckit.clarify`; would require retrofitting all six subcommands' CLI surface later instead of establishing it once now.
- Committing to a full, stable, feature-complete versioned JSON schema now (clarify Option A) — rejected; premature to fully specify a schema for output that doesn't yet represent real behavior.
- Shipping the JSON payload with no version marker at all (the original Option C reading) — rejected during `/speckit.analyze` remediation (finding D1): this would leave the payload literally undocumented/unversioned, in direct conflict with constitution Principle III's unconditional wording. The `schema_version` field is the minimal change that satisfies the letter of the principle without abandoning the "minimal payload for now" scope decision.
- A plain (non-`global`) top-level-only flag, requiring `--human` before the subcommand name exclusively — rejected during post-review remediation, for the same "before or after subcommand" placement-flexibility reasons the original `--format`/`--json` design already established; `global = true` is a one-line clap attribute that makes this correct instead of accidental.
- An `Option<Format>` enum plus a `--json` shorthand boolean, with a `--json`-always-wins conflict rule (the original design) — rejected during a later review pass (PR #1 discussion) in favor of one boolean flag: with only two possible states (JSON by default, human via `--human`), an enum-plus-shorthand and its conflict-resolution rule is strictly more surface area than the problem needs; a single flag has no conflicting-input state to define behavior for at all.
- Human-readable-by-default (the original design) — rejected alongside the above; see Rationale for why JSON-by-default better matches allez's agent-first audience.
- TTY detection (`std::io::IsTerminal`/`is_terminal()`) as the default-selection mechanism, with `--human`/an equivalent explicit flag as an override — considered, since constitution Principle III explicitly permits a "context-aware" default; rejected because it is not a reliable signal of *audience* (human vs. agent), only of *plumbing* (is a pty present in the fd chain). Agent/coding-assistant frameworks commonly allocate a pseudo-terminal around subprocess execution for reasons unrelated to who's consuming the output (enabling color codes, live-streaming progress to their own UI), so `is_terminal()` returning `true` does not imply a human is reading the result — it would misfire specifically for the audience this project is built around. An unconditional JSON default avoids depending on a signal that can't do the job it would be asked to do.

## 3. Structured logging vs. primary output: `tracing` + `tracing-subscriber`, stderr/stdout split

**Decision**: Use `tracing` + `tracing-subscriber` (0.3.x) for structured observability (constitution Principle XI), initialized **once** in `main()` — before subcommand dispatch — based on the parsed `--human` flag, selecting between `.pretty()` (human) and `.json()` (machine, the default) formatters via `tracing_subscriber::fmt()...init()`. All `tracing::*!` log/span events are written to **stderr**. The primary command output contract (FR-013's default JSON result payload) is a **separate concern**, written to **stdout** via `println!`/`serde_json::to_string`.

**Rationale**:
- Formatter selection in `tracing-subscriber` is a startup-time decision (the global subscriber is installed once via `.init()` and cannot be hot-swapped mid-process), which aligns naturally with parsing `--human` before dispatching to a subcommand.
- Separating logs (stderr) from primary output (stdout) is standard Unix CLI practice, confirmed against the Rust CLI Book's own guidance ("Printing errors should be done via stderr... to make it easier for users and other tools to pipe their outputs") — critical for FR-013's machine-readable mode to stay parseable: if log lines leaked onto stdout, a JSON consumer's `serde_json::from_str(stdout)` would break.
- This gives one clean mental model for the whole scaffold: **stderr = diagnostics/logs (human or JSON, per `--human`)**, **stdout = the command's actual result (JSON by default, human text with `--human`, FR-013)**.

**Alternatives considered**:
- Using `tracing`'s output as the primary machine-readable contract (i.e., treating log JSON lines as the "API") — rejected; conflates two different consumers (an operator tailing logs vs. an agent parsing a single result object) and would make FR-013's `schema_version`-tagged result payload awkward to define against a stream of log events.
- `log` + `env_logger` — simpler but lacks `tracing`'s structured span/field model that the constitution explicitly calls for ("consistent fields: operation, package, duration, result"); rejected as insufficient for Principle XI.

## 4. Integration testing: `assert_cmd` + `predicates` (+ `rstest` for table-driven cases)

**Decision**: Black-box integration tests in `tests/` using `assert_cmd::Command::cargo_bin("allez")` to run the actual compiled binary, `predicates` for stdout/stderr/exit-code assertions, and `rstest`'s `#[case(...)]` macro for table-driven coverage across the six subcommands' valid/invalid invocations (satisfies constitution Principle VIII: 100% spec-test coverage, one test per acceptance scenario).

**Rationale**:
- `assert_cmd` + `predicates` (current versions 2.2.x / 3.1.x per `assert-rs/assert_cmd` and `assert-rs/predicates-rs`) is the standard, mature combination for testing a compiled CLI binary end-to-end — necessary here because the spec's acceptance scenarios (User Stories 1-3) are expressed entirely in terms of observable process behavior (stdout/stderr content, exit code), not internal function calls.
- `rstest` table-driven cases keep the ~20+ acceptance-scenario-derived test cases (valid invocations × 6 subcommands, invalid invocations × several failure modes, `--help` variants) from becoming 20+ near-duplicate test functions — satisfies DRY (Principle IV) in the test suite itself.
- Testing the `--` separator specifically requires asserting that tokens after it (including ones that look like flags, e.g. `-c`) are passed through verbatim — a known gotcha flagged in clap's own test suite, which the plan accounts for with a dedicated pass-through test case per subcommand that has one.
- Asserting default (JSON) output requires deserializing captured stdout with `serde_json::from_str` and checking structure (presence of `schema_version`, and of `category` for error bodies) rather than exact string equality — avoids over-specifying the non-version payload fields, which stay intentionally minimal for this ticket.

**Alternatives considered**:
- Calling library functions directly (unit tests only, no `assert_cmd`) — rejected as primary strategy; the spec's contract is explicitly about process-level behavior (exit codes, argv parsing via the real binary), which unit tests calling internal functions can't fully verify. Unit tests still apply for internal logic (constitution Principle II: unit tests live alongside code under test).
- Hand-rolled `std::process::Command` + manual output parsing (no `assert_cmd`) — rejected; reinvents `assert_cmd`'s well-tested assertion/predicate ecosystem for no benefit.
- One test file per subcommand instead of a shared table-driven file — considered and rejected for this ticket's scope (6 subcommands with substantially overlapping shapes); revisit if per-subcommand test logic grows complex enough in later tickets to warrant a split.

## 5. Pass-through argv redaction: default-redacted acknowledgment + `--verbose`/`-v` reveal

**Decision**: The stub acknowledgment for `oneshot`/`run`/`sandbox` (FR-009, FR-016) redacts the captured pass-through `program`/`args` by default — `{"program": "<redacted>", "arg_count": N}` — and reveals the full unredacted value only when a `--verbose`/`-v` global flag (parsed alongside `--human`, same `global = true` mechanism) is present. `packages` and `path` are never redacted.

**Rationale**: A prior review pass (Oracle security lane) identified that this ticket's own stub handlers — not just later tickets' real logging — are the first point at which caller-supplied pass-through argv gets echoed back to stdout/JSON, and that argv may legitimately contain secrets (`allez sandbox -- curl -H "Authorization: Bearer <token>"`). Deferring redaction to a later logging ticket (as the original contract draft's "SHOULD NOT... downstream tickets should gate" language implied) leaves this ticket's own default output actively disclosing secrets from day one. Introducing `--verbose`/`-v` rather than removing the acknowledgment content entirely preserves both: (a) full black-box testability of pass-through parsing correctness (including the flag-like-token-preservation edge case, FR-012) via `--verbose`-mode tests, and (b) constitution Principle III's requirement that human-readable output stay "fully-featured... including verbose/trace output suitable for interactive debugging" — the default just isn't that verbose mode.

**Alternatives considered**:
- Leaving redaction entirely to downstream logging tickets (original draft) — rejected; the exposure already exists in this ticket's own stub output before any logging code is written.
- Redacting `packages`/`path` too, "to be safe" — rejected; these are structural identifiers supplied as allez's own typed arguments (not arbitrary caller-supplied command content), and over-redacting them would defeat FR-009's acknowledgment purpose (proving parsing correctness) for no corresponding secrecy benefit, since package names and paths aren't the vector the security review flagged.
- Hash-based redaction (e.g. a truncated SHA-256 of `program`) instead of `arg_count` — rejected as unnecessary complexity for a stub-only ticket; a plain count is sufficient to prove routing succeeded and is simpler to assert in tests.

## 6. Fixed error `category` enum

**Decision**: The JSON error body's `category` field (FR-011, FR-017) is drawn from one fixed, closed `enum` (Rust-level, serialized as its variant's string form) for this ticket's usage-error surface: `missing_argument`, `unknown_subcommand`, `unknown_flag`, `missing_pass_through_command`.

**Rationale**: The original draft left `category` values as "an implementation decision for this ticket," which a review pass flagged as under-specified for a contract `contracts/cli-schema.md` itself says downstream tickets "MUST NOT change... without a new spec" — an open string invites two independent implementations to choose different literal values for the same logical error, defeating the entire point of a stable machine-readable category. A Rust `enum` (rather than a bare `String`) additionally satisfies constitution Principle VI's "leverage the type system to make invalid states unrepresentable": `AllezError`'s variants already map 1:1 to these four categories (see `src/error.rs` in plan.md's Project Structure), so deriving `category`'s serialized value directly from the enum variant (e.g. via `serde`'s `#[serde(rename_all = "snake_case")]` on `AllezError`, or an explicit `as_category_str()` method) means there is no second, hand-maintained list of category strings to drift out of sync with the error type itself.

**Alternatives considered**:
- Open `String` category (original draft) — rejected; see Rationale.
- A numeric error code instead of a string category — rejected; FR-011 already reserves numeric exit codes exclusively for the 0/2 success/usage-error distinction (SC-004), and a second numeric axis would blur that separation; a string enum keeps the two orthogonal.

## 7. Non-empty `Environment Path` validation: shared clap `value_parser`

**Decision**: A single function `parse_nonempty_path(s: &str) -> Result<String, String>` in `src/cli/mod.rs`, returning `Err` for an empty string, wired as the clap `value_parser` (`#[arg(value_parser = parse_nonempty_path)]`) on `CreateArgs.path`, `RunArgs.path`, and `RemoveArgs.path` — one shared function, not three independent checks.

**Rationale**: `data-model.md`'s Environment Path entity and `spec.md`'s Edge Cases already required empty-string rejection, but the original draft named no implementing mechanism anywhere in plan.md/tasks.md — a review pass flagged this as "tested but not designed": `T031A` asserted the behavior with no task defining how it's achieved. A clap `value_parser` runs during `try_parse()` itself, meaning an empty path is rejected as part of the same standard clap-error path that FR-010/FR-011 already route through `error.rs`'s consistent renderer — no separate post-parse validation branch is needed (unlike `validate_pass_through()`, which genuinely can't be a `value_parser` because it depends on `sandbox` not calling it at all, not on the value itself). Sharing one function across all three subcommands mirrors the DRY pattern this ticket already established for `--` handling (Decision 1) and satisfies FR-015's explicit "one shared, named validation function... not three independent per-subcommand checks."

**Alternatives considered**:
- Three independent inline checks (one per subcommand's handler) — rejected; duplicates the same one-line check three times for no benefit, against DRY (Principle IV).
- A post-parse validation function analogous to `validate_pass_through()` — rejected in favor of a clap `value_parser`; unlike the pass-through-required check (whose required-ness genuinely varies by call site — required for `oneshot`/`run`, optional for `sandbox`), non-emptiness is unconditionally required everywhere `Environment Path` appears, so there's no call-site-specific behavior to preserve by deferring it past `try_parse()`.

| Performance Goals | N/A — arg parsing/routing has negligible, unmeasured cost for this ticket's scope |
| Constraints | `Cargo.lock` committed (constitution IX); builds cleanly on all four target platforms; `--human`/`--verbose` are `global = true` clap flags, JSON is the unconditional default (Decision 2); pass-through argv redacted by default (Decision 5); error `category` is a fixed enum (Decision 6); `Environment Path` non-emptiness enforced by a shared `value_parser` (Decision 7) |
| Scale/Scope | Single-process CLI, six subcommands, no concurrency concerns |
