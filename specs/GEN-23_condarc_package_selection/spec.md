# Feature Specification: Resolve `.condarc` Channel Preferences for Package Selection

**Feature Branch**: `GEN-23_condarc_package_selection`

**Created**: 2026-07-29

**Status**: Draft (revised 2026-07-30 — see Operating Context for the scope change; further refined the same day per follow-up spec review — see Assumptions)

**Input**: User description: "GEN-23 Parse ~/.condarc for package-selection preferences: read the user's ~/.condarc on startup and extract channels, channel_priority, default_channels, and per-channel auth/proxy settings that affect resolution, tolerating missing or malformed files." *(Predates three scope corrections: per-channel auth/proxy extraction is out of scope for this ticket's output — see FR-008 — the channel-resolution algorithm is being added as a new capability of GEN-36's own crate rather than as code inside `allez`, and that new crate-side capability is this ticket's own work to build and test — see Operating Context.)*

**Jira**: [GEN-23](https://anaconda.atlassian.net/browse/GEN-23) — Parse `~/.condarc` for package-selection preferences (parent epic: [GEN-19](https://anaconda.atlassian.net/browse/GEN-19); sub-task: [GEN-36](https://anaconda.atlassian.net/browse/GEN-36))

**Operating Context**: `allez` runs inside a sandbox, invoked by an AI agent rather than a human (see the parent epic). This feature is read-only: it never writes to or manages `~/.condarc`.

As originally drafted, this ticket's work was a single, `allez`-internal piece of code that both located the file and resolved its contents into a concrete channel list. Following review, that changed: the channel-resolution algorithm itself — expanding bare channel names, substituting the `defaults` placeholder, normalizing channel priority, and resolving the allow/deny lists — is generic conda behavior a consumer other than `allez` (starting with nteract's own desktop work) may need independently, so it belongs in the condarc crate (GEN-36) rather than in `allez`.

GEN-36's crate is already delivered, but only as a **parser**: it turns `~/.condarc`'s text into a typed, validated `Config` with **no general defaulting** (per that crate's own FR-038: "a caller that wants a default applies its own policy explicitly"; the one narrow, existing exception is `ParseOptions.null_sequence_map_defaults`, discussed in Assumptions). It does not yet resolve channels — there is today no function in that crate that expands a bare name, substitutes `defaults`, or resolves an allow/deny list. Closing that gap is itself part of this ticket's own work, not a precondition already met elsewhere. Concretely, this ticket's work is delivered in two places, both fully specified below and both tracked, planned, reviewed, and tested entirely under this one ticket — no separate ticket is filed for either part, and GEN-36's own (closed) Jira ticket is not reopened, even though one part lands in a different crate's codebase:

1. **A new, additive channel-resolution capability inside the condarc crate** (`crates/condarc`): an `expand_channels` capability, layered on top of — and never altering — the crate's existing `parse()`/`Config` (see Assumptions). This is generic conda behavior with no dependency on `allez`, independently callable by any consumer of the crate (including a future nteract caller) that wants a fully-resolved channel configuration rather than the raw parsed document.
2. **File handling and adaptation inside `allez`**: locate and read `~/.condarc`, fall back to conda's own documented defaults whenever the file is absent, rejected, or unreadable, hand the file's contents to the crate's `parse()`, hand `parse()`'s result to the crate's new `expand_channels()`, and adapt `expand_channels()`'s output into the four-part shape the ephemeral-environment-creation capability (GEN-24, delivered) requires as input — so the `allez oneshot` capability (GEN-25) can wire the crate and GEN-24 together directly, with no further translation. (An earlier plan for this ticket also included retiring supposedly-duplicate code in `allez`'s existing ephemeral-environment module; on inspection, none of that code turned out to be a genuine duplicate of this ticket's own work — see Assumptions/Design Decisions, "Cleanup boundary".)

Requirements below are grouped by which codebase location implements them (`crates/condarc` vs. `allez`'s own source), but both groups are this one ticket's own deliverable.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Resolve real channel preferences into one ready-to-use list (Priority: P1)

An operator (an AI agent, via the `allez oneshot` capability that wires this ticket's output into environment creation) needs the channels a user has actually configured in `~/.condarc` — bare names, custom channel/multichannel definitions, and the `defaults` placeholder alike — turned into a single, ordered list of concrete channel identifiers, so environment creation honors the user's real preferences instead of a generic guess.

**Why this priority**: This is the core value of this ticket's work — every other behavior (graceful fallback, priority mode, allow/deny) refines this central resolution step.

**Independent Test**: Supplying a populated `.condarc` exercising `channels`, `channel_alias`, `custom_channels`, `custom_multichannels`, and `default_channels` together, verify the resolved output is one flat, ordered list of concrete channel identifiers with every bare name and `defaults` reference already expanded.

**Acceptance Scenarios**:

1. **Given** a `.condarc` that lists one or more channels by bare name, **When** those preferences are resolved, **Then** the output is a single, ordered list of concrete channel identifiers, preserving the original ordering exactly, with each bare name expanded according to this precedence: an already-fully-qualified URL is used as-is; otherwise a matching `custom_multichannels` name, expanded to that multichannel's own members; otherwise a `custom_channels` name matched via progressive prefix stripping; otherwise `channel_alias`.
2. **Given** a `.condarc` whose `channels` list includes the special `defaults` name — or omits `channels` entirely, sets it to an explicit `null`, or sets it to an empty list — **When** those preferences are resolved, **Then** every occurrence of `defaults` is resolved via `custom_multichannels`: the user's own `custom_multichannels.defaults` definition if configured, otherwise the channel(s) from `default_channels`.
3. **Given** a `.condarc` that sets `override_channels_enabled`, **When** those preferences are resolved, **Then** that setting has no effect on the resolved channel list — this ticket's `.condarc`-only input has no separate override-request concept for it to gate.
4. **Given** a `.condarc` that sets `channels` to a non-empty list that does not include the `defaults` placeholder, **When** those preferences are resolved, **Then** the resolved output contains only the channels derived from that list — `default_channels` is not automatically appended alongside it.
5. **Given** a `.condarc` whose `custom_multichannels` definitions include a member entry that itself names another multichannel, a `custom_channels` entry, or the same multichannel being defined, **When** those preferences are resolved, **Then** that member is resolved as an ordinary bare name via `channel_alias` — it is not expanded further.
6. **Given** a `.condarc` that sets both `channels` and its alias `channel`, **When** those preferences are resolved, **Then** this is treated as malformed input, rather than picking one value over the other.

---

### User Story 2 - Never block on a missing or broken preferences file (Priority: P1)

An operator needs environment creation to keep working even when the current user has no `~/.condarc` at all, or has one that is malformed, invalid, or unreadable — the absence or brokenness of a human-authored config file should never be the reason an unattended, agent-driven operation fails.

**Why this priority**: `allez` runs unattended on behalf of an agent; a configuration problem entirely outside `allez`'s control must not block every subsequent operation.

**Independent Test**: Resolve preferences when `~/.condarc` (a) does not exist, (b) exists but the crate rejects its contents, and (c) exists but cannot be read due to an OS permission error — and confirm all three complete successfully using conda's own documented default channel configuration.

**Acceptance Scenarios**:

1. **Given** no `~/.condarc` file exists, **When** channel preferences are resolved, **Then** resolution completes successfully using conda's own documented default channel configuration, with no error surfaced to the caller and no observability record needed for this ordinary, expected case.
2. **Given** a `~/.condarc` file whose contents GEN-36's crate rejects, **When** channel preferences are resolved, **Then** resolution completes successfully using conda's own documented default channel configuration, the same as a missing file, with the condition recorded both through this project's structured observability — using the per-problem detail the crate already produces — and in the resolution result itself (FR-017), rather than being silently indistinguishable from a normal, empty configuration at either level.
3. **Given** a `~/.condarc` file that exists but cannot be read due to an OS permission error, **When** channel preferences are resolved, **Then** resolution completes successfully using conda's own documented default channel configuration, the same as a malformed file, with the condition recorded both through this project's structured observability and in the resolution result itself (FR-017), distinct from the silent "file absent" case in Acceptance Scenario 1 at either level.
4. **Given** any resolution request, regardless of outcome, **When** channel preferences are resolved, **Then** the `~/.condarc` file itself is never modified, moved, or deleted (see FR-013).

---

### User Story 3 - Preserve priority and enforce access-restriction preferences exactly (Priority: P2)

An operator needs a user's declared channel-priority strictness to survive resolution intact, and any explicit channel allow/deny restrictions to actually be applied to the resolved list, so environment creation only ever sees the channels the user meant to allow.

**Why this priority**: This refines User Story 1's core resolved list rather than introducing new mechanics.

**Independent Test**: Resolving a `.condarc` that sets each of the three `channel_priority` string values, plus its two boolean spellings, confirming each resolves to the correct mode; separately, resolving a `.condarc` that sets `allowlist_channels`/`denylist_channels` and confirming the main resolved channel list reflects that filtering (deny-list applied first, then allow-list).

**Acceptance Scenarios**:

1. **Given** a `.condarc` that sets `channel_priority` to `strict`, `flexible`, or `disabled`, **When** those preferences are resolved, **Then** the resolved output carries that exact value.
2. **Given** a `.condarc` whose `channel_priority` key is entirely absent, **When** those preferences are resolved, **Then** the resolved output uses conda's own documented default (`flexible` — see FR-002's defaults table).
3. **Given** a `.condarc` that sets `allowlist_channels` and/or `denylist_channels`, **When** those preferences are resolved, **Then** the main resolved channel list has every denied entry removed, and, if the allow-list is non-empty, every entry not in it removed too — checked against the same concrete identifier form the main channel list uses (FR-004/FR-019).
4. **Given** a `.condarc` that sets both `allowlist_channels` and its alias `whitelist_channels`, **When** those preferences are resolved, **Then** this is treated as malformed input, rather than picking one value over the other.
5. **Given** a `.condarc` that sets `channel_priority` to the legacy boolean spelling `true` or `false`, **When** those preferences are resolved, **Then** `true` resolves to `flexible` and `false` resolves to `disabled`.

### Edge Cases

- What happens when `~/.condarc` does not exist? (Resolution succeeds using conda's own documented default channel configuration, no observability record needed.)
- What happens when `~/.condarc` exists but the crate rejects its contents? (Treated the same as a missing file — resolution succeeds using conda's own documented defaults, with the crate's own per-problem detail recorded via structured observability.)
- What happens when `~/.condarc` exists but cannot be read due to an OS permission or other I/O error? (Treated the same as a malformed file — resolution succeeds, with a minimal condition record via structured observability, distinct from the silent "file absent" case.)
- What happens when `~/.condarc` sets `channels` to an explicit `null` value, an empty list, or omits it entirely? (All three resolve the same as an explicit `channels: [defaults]`.)
- What happens when `~/.condarc` sets the singular `channel` key instead of, or in addition to, `channels`? (`channel` populates the same list `channels` does; both keys present in the same file is malformed input.)
- What happens when `channel_priority` is set to the legacy boolean spelling `true` or `false`? (`true` resolves to `flexible` and `false` resolves to `disabled`.)
- What happens when a `.condarc` setting this ticket's work does not recognize at all is present, and is unrelated to channel/package selection? (Ignored without causing a failure — inherited directly from the crate's own unknown-key tolerance; see FR-014.)
- What happens when a bare channel name matches both a `custom_channels` entry and a `custom_multichannels` entry? (The `custom_multichannels` match takes precedence — see FR-001(b) before FR-001(c).)
- What happens when a bare channel name is a sub-path under a `custom_channels` entry's name rather than an exact match (e.g. `acme/label/dev` when `custom_channels` configures `acme`)? (Matched via progressive prefix stripping, resolved using the matched entry's base URL joined with the *original, full* name.)
- What happens when the same channel appears in both `allowlist_channels` and `denylist_channels`? (Denial takes precedence — FR-019 checks the deny-list first, so that channel is removed from the resolved list regardless of also being present in the allow-list.)
- What happens when `~/.condarc` triggers one of the crate's own documented parsing divergences from real conda (an out-of-range integer in an integer-typed setting, a non-ASCII decimal digit in a numeric-parsed setting, an over-1024-character YAML key, or a pathologically deep/large document)? (Bounded entirely by the crate's own behavior, not re-validated by this ticket's work — see Known Limitations.)
- What happens when resolving a channel-list entry requires joining it to an explicit, empty-string `channel_alias`? (`expand_channels()` returns `Err(ExpandChannelsError::EmptyChannelAlias)` — FR-018 — which `allez` treats the same as a rejected file, FR-011.)
- What happens when the resolved channel list, after FR-019's deny/allow filtering, is empty? (A fully successful resolution, not an error — see FR-020 and Design Decisions, "Empty resolved list" — `allez`'s own resolution result records this distinctly so GEN-24's `channels_with_fallback` never mistakes it for "nothing was configured.")

## Requirements *(mandatory)*

### Channel Resolution (new capability to be added to the condarc crate — `crates/condarc`)

- **FR-001**: MUST resolve the user's configured channels — populated via `channels` or its alias `channel` (both present in the same file is malformed input), or conda's own effective default of a single `defaults` entry when absent or empty — into a single, ordered list of concrete channel identifiers (see Key Entities), preserving original ordering, via this precedence: (a) an entry matching conda's own scheme pattern (`^[a-z][a-z0-9]{0,11}://`, e.g. `https://`, `file://`), used as-is; (b) a `custom_multichannels` name, expanded to that multichannel's own members (the name `defaults` is always resolved here first); (c) a `custom_channels` name matched via progressive prefix stripping, joined with the entry's original full name (`base_url.trim_end_matches('/') + "/" + entry`); (d) otherwise, joined with `channel_alias` the same way (`channel_alias.trim_end_matches('/') + "/" + entry`).
- **FR-002**: MUST apply conda's own documented default for any relevant setting whose key is absent from `~/.condarc`, distinguishing an absent key from an explicit `null` and an explicit empty list/map exactly as conda itself does. This defaulting is a property of the new `expand_channels` capability only; it MUST NOT alter `parse()`'s own existing, unchanged behavior of representing an absent setting as absent (see Assumptions). The exact default alias, platform-specific `default_channels` value, and built-in `custom_channels` mapping are conda's own already-documented default constants (see `docs/condarc_research.md` and the condarc crate's own already-delivered handling of them), not values this ticket invents:

  | Setting | Default when key absent | Explicit `null` | Explicit empty (`[]`/`{}`) |
  |---|---|---|---|
  | `channels` (or its alias `channel`) | Single `defaults` entry | Same as absent — single `defaults` entry | Same as absent — single `defaults` entry |
  | `channel_alias` | Conda's documented default alias | Malformed † | N/A — not list/map-shaped |
  | `default_channels` | Platform-specific conda default | Same as absent — conda's default applies | Distinct, valid value — stays empty, not defaulted |
  | `custom_channels` | Conda's built-in `pkgs/pro` mapping | Same as absent — conda's default applies | Distinct, valid value — stays empty, not defaulted |
  | `channel_priority` | `flexible` | Malformed † | N/A — not list/map-shaped |
  | `allowlist_channels` (or alias `whitelist_channels`) / `denylist_channels` / `custom_multichannels` | Empty (`()`/`{}`) | Same as absent | Same as absent — already empty regardless |

  † `parse()` rejects an explicit `null` on this scalar setting outright (a whole-document rejection, not setting-level defaulting); FR-011's whole-file fallback applies, the same as any other crate-rejected document.

  An explicit, non-empty value for any setting in this table is used exactly as given, with no merge against the corresponding built-in default — this ticket's single-document scope has no multi-source merge concept for any setting, matching GEN-36's own Target Platform boundary.

- **FR-003**: MUST resolve `channel_priority` to exactly one of conda's own three documented modes (`strict`, `flexible`, `disabled` — defaulting to `flexible` per FR-002's table when the key is absent), including its legacy boolean spellings (`true`→`flexible`, `false`→`disabled`).
- **FR-004**: MUST resolve the channel allow-list (`allowlist_channels`, alias `whitelist_channels`) and deny-list (`denylist_channels`) through the same precedence FR-001 defines, so every entry uses the same concrete-identifier form as the main channel list, then apply them directly to the main resolved channel list — denied entries removed first, then, only if the resolved allow-list is non-empty, every entry not in it removed too (see FR-019) — rather than expose the two lists as separate output fields. Both lists default to empty when their setting is absent, in which case the main list passes through unfiltered.
- **FR-005**: MUST treat a document that sets both a setting's canonical name and its alias (`channels`/`channel`, `allowlist_channels`/`whitelist_channels`) as malformed input, rather than picking one value over the other. This is a `parse()`-level rejection (an alias collision, the same category `parse()` already detects for any other setting), not an `expand_channels()`-level decision — a document with such a collision never reaches `expand_channels()` at all; it takes the whole-document fallback path FR-011 already defines.
- **FR-006**: MUST NOT apply `override_channels_enabled` to the resolved channel list — this ticket's `.condarc`-only input has no separate override-request concept for it to gate.
- **FR-007**: MUST NOT add a deduplication pass of its own over the resolved channel list, allow-list, or deny-list: a literal, raw duplicate within one setting's own list is already removed by `parse()`'s own sequence handling (matching conda's own merge-time `unique()` behavior) before resolution ever sees it, so resolution has nothing left to deduplicate there — but if resolving two different entries happens to coincide on the same concrete identifier (e.g., two different bare names that both expand to the same URL), that coincidental repeat is preserved as-is, not collapsed.
- **FR-008**: MUST NOT include per-channel authentication or proxy settings (`channel_settings`) anywhere in the resolved output.

### File Handling and Adaptation (in `allez`)

- **FR-009**: MUST locate and read `~/.condarc`, tolerating its absence by proceeding with conda's own documented default channel configuration rather than failing, with no observability record needed for this ordinary, expected case. This absence case includes not just a missing file at a known path, but also the path itself being undeterminable (e.g. no resolvable home directory) — both are equally "the file cannot be located" from this capability's perspective, and neither is treated differently.
- **FR-010**: MUST hand `~/.condarc`'s contents to the condarc crate's `parse()`, and hand `parse()`'s result to the crate's `expand_channels()`, for parsing and channel resolution respectively; MUST NOT re-implement any part of either.
- **FR-011**: MUST tolerate a `~/.condarc` file the crate's `parse()` rejects, one that exists but cannot be read due to an OS permission or other I/O error, or one that parses successfully but whose `expand_channels()` call returns `Err` (FR-018), by proceeding with conda's own documented default channel configuration, the same as a missing file, while recording the specific condition — including the crate's own per-problem detail, for both the rejected-content and the failed-expansion case — through structured observability, distinct from the silent "file absent" case in FR-009. What counts as "rejects" here is bounded entirely by the crate's own documented behavior, including its own accepted divergences from real conda's validation (see Known Limitations) — this ticket's work does not re-validate, tighten, or loosen what the crate itself accepts or rejects. This condition is also surfaced directly in the resolution result itself, not only via observability — see FR-017.
- **FR-012**: MUST adapt the crate's resolved channel configuration into the four-part shape the ephemeral-environment-creation capability (GEN-24) requires as input — an ordered list of concrete channel identifiers, a channel-priority mode, an allow-list, and a deny-list, all always present (never absent, even when empty) — via a direct, lossless, field-by-field construction requiring no additional resolution or transformation logic (see Key Entities and SC-001), except in the FR-020 zero-usable-channels case, where no `ChannelConfig` is constructed at all.
- **FR-013**: MUST NOT write to, modify, or otherwise manage `~/.condarc`.
- **FR-014**: MUST NOT fail, and MUST proceed through ordinary resolution, when `~/.condarc` contains a setting this ticket's work does not itself recognize and that is unrelated to channel/package selection. This is inherited directly from the condarc crate's own unknown-key tolerance and MUST NOT be separately re-implemented, narrowed, or weakened by `allez`'s own handling.
- **FR-015**: MUST resolve fresh from `~/.condarc` on every invocation; MUST NOT cache or reuse a previous resolution result across separate invocations.
- **FR-016**: MUST NOT remove, weaken, or reimplement any of `allez`'s existing, already-delivered ephemeral-environment behaviors that happen to overlap in subject matter with this ticket's own work — specifically GEN-24's empty-channel-list fallback (GEN-24 FR-015), GEN-24's allow/deny filtering (`filter_channels()`, called from GEN-24's own `solve_packages()`), and GEN-24's defense-in-depth credential redaction on channel identifiers it formats (GEN-24 FR-003/FR-013) — on the mistaken assumption that this ticket's `expand_channels()` capability (FR-001–FR-004, FR-005–FR-008, FR-018–FR-019) supersedes them: each MUST keep passing its own existing, already-delivered GEN-24 tests unchanged after this ticket's adaptation layer (FR-012) is wired in (see Assumptions/Design Decisions, "Cleanup boundary", for why none of them is actually a duplicate). `allez`'s existing credential-redaction function is separately used for unrelated, non-channel-config purposes (redacting package-spec strings in error/debug output); this FR does not require touching that usage either. FR-019's crate-local deny-then-allow filtering is a second, independent implementation of the same policy for `condarc`'s own consumers (see Assumptions, "Two independent implementations of the same filtering policy") — it does not call, wrap, or alter `filter_channels()` in any way, and this FR's prohibition on reimplementing `filter_channels()` applies to `allez`'s own codebase, not to a different capability's independent implementation inside a different crate.
- **FR-017**: MUST expose, as part of the resolution result itself — not solely via the structured-observability record FR-011 already requires — whether this call's fallback was caused by a rejected or unreadable `~/.condarc` (FR-011), distinct from the ordinary missing-file case (FR-009), so a caller (e.g. the `allez oneshot` capability, GEN-25) can decide how to react — warn, proceed, or abort — without needing to separately consult observability output. MUST NOT expose any such signal for the missing-file case, which remains indistinguishable from a fully successful resolution at the result level, exactly as it already is via observability. MUST NOT alter GEN-24's own four-part `ChannelConfig` shape (FR-012) to carry this signal — it is a property of the resolution result that produces that shape, not a new field added to the shape itself.

### Channel Resolution

- **FR-018**: MUST return `Result<ResolvedChannels, ExpandChannelsError>` rather than an infallible value, so a caller can distinguish "resolved successfully" from "could not be resolved" instead of that distinction being unavailable at the type level (per review feedback that a crate-level `Result` is more appropriate here than at the `allez` wrapper — see Assumptions). The only case that produces `Err` is `ExpandChannelsError::EmptyChannelAlias`: resolving a channel-list entry (main list, allow-list, or deny-list, or a `custom_multichannels` member) that needs `channel_alias`-joining (FR-001(d)/the restricted `resolve_member` precedence) while the effective `channel_alias` is an explicit empty string — the one corner Known Limitations previously called "unspecified"; this FR turns that corner into a typed, catchable condition instead of leaving it undefined. Every other input configuration MUST still resolve successfully, including one that legitimately resolves to an empty `channels` list (see Design Decisions, "Empty resolved list").
- **FR-019**: MUST apply FR-004's deny-then-allow filtering (deny-list checked first; if the resolved allow-list is non-empty, only entries present in it survive) as a fresh, `condarc`-crate-local implementation of that same policy, independent of and never calling into `allez`'s own already-delivered `filter_channels()` — the crate architecturally cannot depend on `allez` (the reverse of the crate's own dependency direction) — see Assumptions, "Two independent implementations of the same filtering policy," for why this is not the reimplementation FR-016 forbids.

### File Handling and Adaptation

- **FR-020**: MUST distinguish, in the resolution result itself, a resolution that legitimately produced zero usable channels (FR-019's filtering removed every entry, or the underlying configuration otherwise resolves to an empty list with no allow-list to populate it) from every other outcome, and MUST NOT construct a `ChannelConfig` for that case at all. This exists because GEN-24's own, unmodified `channels_with_fallback` (GEN-24 FR-015) treats *any* empty `ChannelConfig.channels` as "nothing was configured" and silently substitutes the `defaults` channel — a correct behavior for GEN-24's own original callers, but one that would silently override a user's own explicit, fully-resolved deny/allow restriction if this ticket's adaptation layer (FR-012) ever handed GEN-24 an intentionally-empty `ChannelConfig`. This is a result-level distinction only, not a new failure mode: it is not the same thing as FR-018's `Err` (a resolution that could not be computed at all) or FR-011's rejected/unreadable-file fallback — an empty-after-filtering result is a fully successful resolution of the user's own real preferences (see Design Decisions, "Empty resolved list").
- **FR-021**: MUST redact any URL userinfo (`user[:pass]@`) or access-token path segment (`/t/<segment>/`) out of the per-problem detail text FR-011's structured observability record carries, applying that redaction independently to every URL-shaped substring the text contains (not only the first), and MUST bound that detail text to 2048 bytes, truncated at the nearest UTF-8 character boundary at or before that length. This applies independently of, and in addition to, FR-011's requirement to record the detail at all — the crate's own rejection/error text is otherwise untrusted, `.condarc`-derived content, and this ticket's own new observability event is the one place that content is emitted through a channel (structured logs) a caller may not otherwise expect to carry it.

### Key Entities *(include if feature involves data)*

- **User Channel Preferences**: The raw `~/.condarc` document as the user has configured it (or its absence). Read-only input to this ticket's work; never written to or otherwise managed by `allez`.
- **Resolved Channel Configuration**: The four-part artifact produced by the condarc crate's `expand_channels()` capability and adapted by `allez` into GEN-24's required shape (falling back to conda's own documented defaults wherever `~/.condarc` is missing, unreadable, rejected, or fails to expand — FR-018): an ordered list of concrete channel identifiers, already filtered by allow/deny (FR-019), a channel-priority mode, and GEN-24's own allow-list/deny-list fields, always present but always empty in this ticket's own output now that filtering has already happened (see FR-004/FR-019) — GEN-24's own `filter_channels()` still runs unmodified at environment-creation time for every caller, this ticket's own output just gives it nothing left to remove. This is the artifact every downstream capability that needs real channel preferences actually consumes, with no further translation, *except* the FR-020 zero-usable-channels case, where `allez`'s own resolution result carries no `ChannelConfig` at all rather than an empty one (see that FR). `allez`'s own resolution result (FR-009–FR-011, FR-012–FR-020) pairs this four-part artifact with the FR-017 fallback-reason signal alongside it, a sibling to, never a fifth part of, this entity, and with the FR-020 zero-usable-channels distinction as an alternative to producing it at all.
- **Concrete Channel Identifier**: The form every entry in the resolved channel list takes once FR-001's precedence rule has been applied — a fully-qualified channel URL in every supported case, including the `defaults` placeholder and any `custom_multichannels`/`custom_channels` bare name, since each of those resolves to a URL (through `channel_alias`, a multichannel's own members, or a `custom_channels` base-URL join, respectively). GEN-24's own consuming field (`ChannelSpec.url_or_name`) is a plain, opaque string that would also accept a bare name — but this ticket's work never hands it one; adapting a fully-qualified URL into that field is a direct, lossless string assignment (see FR-012), not a claim that no construction code exists at all.
- **Channel Priority**: One of exactly three modes (`strict`, `flexible`, `disabled`) governing how strongly earlier channels in the resolved list are preferred over later ones during package resolution.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A caller obtains the complete four-part resolved channel configuration from any `.condarc` input within this ticket's supported scope that resolves to at least one usable channel (populated, missing, rejected, unreadable, or one whose expansion fails per FR-018 — subject to the documented Known Limitations, notably GEN-36 Assumption A5's process-abort exception, and to FR-020's `NoChannels` case, where no `ChannelConfig` is produced at all) — in exactly the shape the ephemeral-environment-creation capability (GEN-24) requires as its own input, constructible via a direct, lossless, field-by-field mapping with no additional resolution or transformation logic needed (its allow-list/deny-list fields always empty, per FR-019's upstream filtering), verified by a dedicated contract test that constructs GEN-24's actual input type directly from the resolved output for at least 5 distinct, real-world-shaped `.condarc` samples.

## Assumptions

### Dependency & Process

- **GEN-36 boundary**: see Operating Context above for why this ticket spans both the condarc crate and `allez`. GEN-36's own Jira ticket stays closed; the crate-side `expand_channels()` work is planned, implemented, and reviewed entirely under this ticket, in `crates/condarc`. This mirrors `ParseOptions.null_sequence_map_defaults` (GEN-36 Assumption A7), an existing narrowly-scoped opt-in that resolves one case to a conda default without touching FR-038's general no-defaulting posture — `expand_channels()` follows the same additive-opt-in spirit as a separate function rather than a `ParseOptions` flag, since it does substantially more (full bare-name expansion and allow/deny resolution).
- **GEN-24 contract**: GEN-24 (delivered) defines the four-part input shape this ticket's adapted output must match (FR-012). GEN-25 (`allez oneshot`) is the production caller: it reads `~/.condarc` through this ticket's work and passes the result to GEN-24 directly.
- **No CLI or human-facing surface of its own**: this ticket's output is for a consuming capability to use directly. The one exception is a manual, optional, developer-run diagnostic (`cargo run --example`) that exercises the public entry point against whatever `~/.condarc` exists on the machine running it — a local development aid, not a shipped command surface, and outside Constitution III's dual-primary-interface scope for that reason.

### Design Decisions

- **Empty resolved list, two legitimate causes**: the resolved channel list can end up empty for two non-bug reasons: a user explicitly configuring an empty `custom_multichannels`/`default_channels` definition, or FR-019's allow/deny filtering removing every entry. Neither is an error (FR-018's `Err` is reserved for `EmptyChannelAlias` only) — but both need `allez`'s FR-020 distinction so GEN-24's `channels_with_fallback` never mistakes either for "nothing was configured."
- **Malformed/unreadable/unexpandable = missing, for resolution purposes**: `allez` runs unattended on behalf of an AI agent, so a `.condarc` problem outside its control must not block every subsequent operation — FR-011 treats a crate-rejected, unreadable, or expansion-failing (FR-018) file the same as an absent one. The resulting `ChannelConfig` never differs between these cases; what differs is that rejected/unreadable/unexpandable cases are distinguished from the silent missing-file case both via observability (FR-009/FR-011) and, per FR-017, in the resolution result itself — so a caller with more context (e.g. GEN-25) can choose to treat the condition as an error, without this ticket's own function ever failing outright. This answers 2026-07-29 spec-review feedback proposing the `allez` helper instead return the configuration or an error: the step stays total, but the fallback condition is now visible inline, not only after the fact via observability.
- **Allow/deny value-level conflicts are now reconciled by construction**: a channel in both the resolved allow-list and deny-list is removed by FR-019's deny-first filtering, matching real conda's own "denylist checked first" precedence (see Known Limitations). This is a deliberate change from the earlier design, where both lists passed through unreconciled for a downstream capability to compare — a direct consequence of FR-019 combining the three lists into one. Distinct from an alias *collision* (both `allowlist_channels` and `whitelist_channels` as keys), which is malformed input (FR-005) and never reaches filtering.
- **Two independent implementations of the same filtering policy**: FR-019 requires `expand_channels()` to apply the same deny-then-allow *precedence* `allez`'s `filter_channels()` (`src/ephemeral/channels.rs`, GEN-24) applies at environment-creation time — not byte-identical semantics: `filter_channels()` matches a `ChannelSpec.url_or_name` verbatim (including the literal bare name `"defaults"`, deliberate per `DEFAULTS_CHANNEL_NAME`'s own doc comment), while `expand_channels()`'s copy matches already-expanded, fully-qualified identifiers on both sides. This isn't the reimplementation FR-016 forbids: that prohibition is scoped to `allez`'s own codebase duplicating its own logic; this copy lives in a different crate for a different consumer, and can't call `filter_channels()` at all — `crates/condarc` architecturally cannot depend on `allez` (research.md R7). `filter_channels()` is untouched, still called from `solve_packages()`; this ticket's adaptation layer (FR-012) just hands it a `ChannelConfig` whose allow/deny fields are already empty, since FR-019 filtered upstream. Recorded honestly: no other call site in `allez`'s current source constructs a `ChannelConfig` with a non-empty allow/deny list either (`ChannelConfig::from_urls` hardcodes both empty; `solve_packages` only forwards what it's given) — `filter_channels()`'s allow/deny branch remains exercisable by any future/external caller that builds a `ChannelConfig` directly, a currently-quiet, not orphaned, function.
- **Cleanup boundary**: none of `allez`'s existing ephemeral-environment behaviors are a genuine duplicate of this ticket's work: `allez`'s defense-in-depth credential redaction independently fulfills GEN-24's own contract (GEN-24 FR-003/FR-013) for *any* caller/channel identifier, not only the `.condarc`-sourced case. Its empty-channel-list fallback (GEN-24 FR-015) covers the *initially-supplied* empty-list case specifically; it explicitly excludes the allow/deny-filtering-caused case, which still fails cleanly — now caught one layer earlier by this ticket's FR-020 before it reaches GEN-24 at all. `filter_channels()` remains GEN-24's own function at its own call site for every other caller (see "Two independent implementations," above). Retiring any of GEN-24's delivered behaviors would regress its guarantees, not remove a duplicate — FR-016 exists to prevent that regression, not to perform a cleanup.

### Known Limitations (Out of Scope)

| Behavior / Input | What real conda does | What this ticket's work does instead | Why it's out of scope |
|---|---|---|---|
| GEN-36's own numeric-parsing divergences (crate Assumptions A1, A4) | Accepts arbitrary-precision integers in any integer-typed setting (A1), and any Unicode decimal digit in a numeric-parsed setting (A4) | Rejects an out-of-range integer (A1) or non-ASCII decimal digit (A4) as ordinary crate-rejected content (FR-011) — an over-rejection relative to real conda | Delegated to the crate; see GEN-36 Assumptions A1/A4 |
| Empty-string `channel_alias` | Accepted (scheme check skipped for this value), but the resulting join is not a meaningful URL | Returns `Err(ExpandChannelsError::EmptyChannelAlias)` (FR-018) — a typed rejection where real conda silently constructs a non-meaningful URL | No evidence any real `.condarc` sets this to empty; reproducing conda's non-meaningful-URL construction would add complexity for a case nothing triggers |
| Empty-string, whitespace-only, or whitespace-padded bare channel-list entries | `Channel.from_value()` has documented handling for these shapes | FR-001's precedence rule defines no separate scheme-detection/trimming/empty-entry behavior beyond ordinary `channel_alias` expansion | No evidence real `.condarc` samples contain such entries; reproducing `Channel.from_value()`'s full shape-detection is out of scope |
| GEN-36's own YAML key-length gap (crate Assumption A6) | Rejects a YAML simple key longer than 1024 characters | Accepts it (including as a `custom_multichannels` key) — an under-rejection, since this ticket never re-validates what the crate already accepted | Delegated to the crate; see GEN-36 Assumption A6 |
| GEN-36's own stack-depth guard gap (crate Assumption A5) | Raises a catchable error for a pathologically deep/large document | Has no equivalent guard; can abort the whole process rather than return a typed rejection | Documented, accepted crate limitation (GEN-36 A5) — User Story 2's "never block" guarantee doesn't cover a process abort |
| `custom_channels` via multichannel-member flattening | `context.custom_channels` also includes every multichannel's own member names | Matches only against the effective `custom_channels` map, no member-flattening | No evidence any real `.condarc` relies on this |
| Schemeless `custom_channels` value | Falls back to `channel_alias`'s location | Unspecified — an out-of-scope corner | No evidence any real `.condarc` configures this |
| `local` multichannel (conda-build) | Refers to a local package-build output directory | Treated as an ordinary bare name, expanded via `channel_alias` | Conda-build workflows are outside the parent epic's scope |
| Local filesystem path channel entries | Converted to a `file://` URL before custom-map lookup | Treated as an ordinary bare name, expanded via `channel_alias` | No expected need for local-path channels in this ticket's target usage |
| URL canonicalization / channel equality | Parses and compares channels by parsed location/name/platform components | Treats a URL entry as an opaque string; no normalization | Reproducing conda's full URL-parsing/equality model is a materially larger undertaking |
| Recognized platform/subdir suffix (e.g. `defaults/linux-64`) | Stripped before lookup; platform applied to every resulting member | Left embedded in the entry's text, no platform semantics | Platform/subdir selection is `allez`'s own downstream, environment-creation-time concern |
| "Unknown channel" sentinel / package-artifact filename | Special-cased | Resolved as an ordinary entry | Not a `.condarc`-configured channel-selection concept |
| `channel_settings` (per-channel auth/proxy) | Configures per-channel auth/proxy behavior | Never appears in the resolved output (FR-008) | Deferred to GEN-29 (private-channel-authentication); GEN-29 must source it independently — an intentional gap, not an oversight |
| `migrated_channel_aliases` / `migrated_custom_channels` | Legacy channel-migration settings | Not resolved at all | Out of scope; only settings known downstream consumers need are resolved |
| `allow_non_channel_urls` (default `false`) | Checked when actually fetching repodata over the network — not part of channel parsing/URL construction | Not read or acted on | `expand_channels()` is pure/no-I/O (FR-001); this setting only matters at a later, network-bound step this ticket never reaches |
| `add_anaconda_token` (alias `add_binstar_token`, default `true`) | Appends an Anaconda access token to certain resolved channel URLs when making an outgoing, authenticated request against them (repodata fetch, package download, or similar) — a request-time transformation, not part of channel parsing/URL construction (`Channel.from_value()` builds the same concrete URL either way) | Not read or acted on; the resolved Concrete Channel Identifier never reflects a token this setting would add at request time | Same rationale as `allow_non_channel_urls` above — token injection happens at a later, network-bound step this ticket's scope never reaches |
| `repodata_fns` | Selects which repodata filename(s) to request from an already-resolved channel, tried in order | Not read or acted on; has no effect on channel selection | Not a channel-selection setting — it governs which file is fetched from a channel this ticket has already resolved, a later, network-bound step |
| Real conda's own `allowlist_channels`/`denylist_channels` enforcement (raises `ChannelNotAllowed`/`ChannelDenied`) | An exclusive validation gate that aborts the operation outright, denylist checked first | Resolves both lists and applies the same deny-then-allow precedence to the main list (FR-004/FR-019), silently removing non-survivors — never raising or aborting | Matching conda's error-raising semantics is a separate decision, out of scope; this ticket's silent filter matches the *spirit* of `allez`'s own `filter_channels()` (GEN-24) — see Assumptions, "Two independent implementations of the same filtering policy" |
