# Phase 0 Research: Ephemeral Environment Default Packages and User Overrides

## Decision: Share `.condarc` document resolution via a new `channel_config::document` submodule

**Decision**: A new, private submodule, `src/channel_config/document.rs` — nested inside the existing `channel_config` module, not a new crate-root file — owns the one new entry point both consumers need: a three-way sum type rather than a tuple (see "Decision: `CondarcDocument` is a sum type, not a tuple" below):

```rust
pub(crate) enum CondarcDocument {
    /// No usable `.condarc` at all — the silent missing-file case
    /// (GEN-23's own spec.md FR-009, whose silent-missing semantics
    /// FR-001 requires reusing here). Every consumer treats this
    /// identically to a document that exists but configures nothing.
    Absent,
    /// The file exists but is unreadable, or `condarc::parse()`
    /// rejected it — `emit_fallback(reason, ...)` has already been
    /// called exactly once before this variant is returned.
    FellBack(FallbackReason),
    /// A successfully located, read, and parsed document.
    Parsed(condarc::Config),
}

pub(crate) fn resolve_document_from(path: Option<&Path>) -> CondarcDocument;
pub(crate) fn resolve_document() -> CondarcDocument;
```

`document.rs` builds directly on `channel_config`'s existing `locate::read_condarc`, `super::default_condarc_path`/`super::condarc_path_override` (private free functions defined in `channel_config/mod.rs` itself, not in `locate.rs`), and `events::emit_fallback`/`events::FallbackReason` — every one of these stays exactly where it already is, at its current `pub(super)`/`pub` visibility, since Rust module privacy is tree-scoped: a sibling submodule under the same parent (`channel_config`) already sees `pub(super)` items without any visibility change. No file is moved, renamed, or deleted; `FallbackReason` needs no re-export gymnastics, since `document.rs` (like `channel_config`'s own `mod.rs`) simply uses `events::FallbackReason` directly.

`resolve_document_from(None)`'s contract: `None` means "no path was supplied for this call" (the test seam for exercising the missing-path case directly) and resolves to `CondarcDocument::Absent` outright, without attempting `default_condarc_path()` — it does **not** mean "fall back to resolving the default path." The only caller that wants "use whichever path `ALLEZ_CONDARC_PATH`/`dirs::home_dir()` resolves to" is the no-argument `resolve_document()`, which explicitly passes `default_condarc_path().as_deref()` into `resolve_document_from` — the same delegation shape `resolve_channel_config()` → `resolve_channel_config_from(default_condarc_path().as_deref())` already uses.

`src/cli/oneshot.rs` calls `channel_config::resolve_document()` (defined in `document.rs`, re-exported at `channel_config`'s own module root since `document` itself is a private submodule) **exactly once** per invocation and hands the resulting `&CondarcDocument` to two independent functions, neither of which reads or re-reads `~/.condarc` itself:

- `channel_config::channels_from_document(document: &CondarcDocument) -> ChannelConfigResolution` — the channel-specific expansion step (`condarc::expand_channels`), which performs no file I/O of its own but may itself call `emit_fallback` a second time if `document` is `Parsed` and its own channel settings fail `condarc::expand_channels`.
- `default_packages_config::create_default_packages_from_document(document: &CondarcDocument) -> Vec<PackageSpec>` (new, § below) — the `create_default_packages` extraction step, infallible and free of any observability side effect of its own.

`channel_config::resolve_channel_config()` (`pub`) and `resolve_channel_config_from()` (`pub(crate)`) — GEN-23's existing API, at their existing visibilities — keep their exact signatures and behavior for any standalone caller: internally, `resolve_channel_config_from(path)` calls `document::resolve_document_from(path)` then `channels_from_document()`; the no-argument `resolve_channel_config()` calls the correspondingly no-argument `document::resolve_document()` then `channels_from_document()` — each composes with the arity-matching `resolve_document`/`resolve_document_from` variant, not the same one.

**Rationale**: FR-001 requires default-package resolution to use "the exact same `~/.condarc` location and missing-or-malformed-file fallback semantics GEN-23 already establishes... not a new, separate `allez`-specific config mechanism." Sharing the implementation, rather than reimplementing it a second time for default packages, is the literal way to guarantee "exact same" rather than "behaviorally similar" (Constitution IV, DRY); reading `~/.condarc` once and handing the parsed document to both downstream functions also avoids double-emitting a fallback event for one underlying fact. Nesting the new logic inside `channel_config` rather than extracting it into a new crate-root module keeps that guarantee without moving or deleting any existing file: `locate.rs`/`events.rs` already own exactly the I/O and fallback-observability logic this ticket needs to share, so `document.rs` reuses them in place as a sibling submodule instead of relocating their content elsewhere first.

**Alternatives considered**: Giving `default_packages_config` its own independent copy of the read/fallback logic was rejected — directly contradicts FR-001's "not a new, separate... mechanism" (two independently-implemented copies of the same fallback classification could drift). Extracting a brand-new crate-root module (`src/condarc_source.rs`) and physically moving `locate.rs`/`events.rs` out of `channel_config` into it was considered and rejected as unnecessary churn: it would delete and relocate two existing, already-tested files purely to change where a new type lives, when nesting `document.rs` inside `channel_config` shares the same underlying I/O with no file move at all. Folding default-package resolution directly into `channel_config` itself (rather than a new `document` submodule within it) was also rejected: `create_default_packages` has nothing to do with channels, and piling an unrelated setting onto `channel_config`'s own public surface would violate Constitution I's single-responsibility rule — `document.rs` solves this by keeping the shared I/O nested where it's used without exposing default-package semantics through `channel_config`'s own public API.


## Decision: `CondarcDocument` is a sum type, not a tuple

**Decision**: `resolve_document[_from]` (defined in `channel_config::document`, re-exported at `channel_config`'s own module root) returns the three-variant `CondarcDocument` enum shown above, not a `(Option<condarc::Config>, Option<FallbackReason>)` tuple.

**Rationale**: The three real states — "no file at all," "a file existed but resolution fell back," and "a file parsed successfully" — are mutually exclusive by construction (a document that fell back never also carries a parsed `Config`, and the silent-missing case never carries a `FallbackReason`). A `(Option<Config>, Option<FallbackReason>)` tuple admits a fourth combination, `(Some(config), Some(reason))`, that no code path ever produces and that has no defined meaning — an invalid state the type itself fails to rule out. Constitution V (Explicit Over Implicit) requires leaning on the type system to make invalid states unrepresentable rather than relying on a caller to just never construct that combination; a three-variant enum does this for free, at no extra implementation cost over the tuple.

**Alternatives considered**: A `(Option<condarc::Config>, Option<FallbackReason>)` tuple shape (matching this codebase's pre-existing `resolve_channel_config_from`-internal convention of returning `(ResolvedChannels, Option<FallbackReason>)`-shaped pairs) is rejected specifically because, unlike that existing pair (whose two fields are independently meaningful — a resolution always has channels, and independently may or may not have fallen back), this new document-resolution step's three states are mutually exclusive alternatives of the same underlying fact, which an enum expresses directly and a tuple does not.

## Decision: Bare package name extraction via a `MatchSpec` name matcher

**Decision**: `PackageSpec` (`src/ephemeral/defaults.rs`) gains

```rust
pub(crate) fn bare_name(&self) -> Option<String>
```

implemented by re-parsing the opaque string via `rattler_conda_types::MatchSpec::from_str(self.as_str(), ParseStrictness::Strict)` and returning `parsed.name.as_exact().map(|name| name.as_normalized().to_string())` on success — `Some` when the reparse succeeds and yields an exact name matcher, `None` otherwise (including when the reparse fails outright). For a `PackageSpec` built via the validating `PackageSpec::parse` (every per-invocation entry), this is always `Some`: `ParseStrictness::Strict`'s own `exact_names_only: true` already guarantees an exact name matcher at construction time. For a `PackageSpec` built via `PackageSpec::from_resolved_default` (every default-sourced entry), the reparse can genuinely fail — an empty or whitespace-only string is exactly this case — and `bare_name()` returns `None`: there is no bare name to compare this entry by, so it can never be recognized as colliding with, or being collided into by, any other entry (`effective_packages`, below, always keeps a `None`-bare-name `defaults` entry). It reaches the solver on its own, unaffected by the merge, exactly as any other default entry would be.

**Rationale**: FR-004 compares by "bare package name" — the name portion only, "regardless of which of the two carries a version or build constraint," which also means regardless of channel/subdir. `rattler_conda_types::PackageName::from_matchspec_str_unchecked` (a cheaper, no-full-reparse alternative, rejected below) only scans for whitespace/version-operator/`[` delimiters — it does **not** stop at `::`, so it returns `conda-forge::numpy` verbatim for a channel-qualified spec, not `numpy`. A per-invocation `conda-forge::numpy` and a default-set bare `numpy` must still be recognized as the same package for FR-004's supersede rule to fire at all in the (common) case where only one side happens to name a channel — `from_matchspec_str_unchecked` cannot do this; only going through the full `MatchSpec` parse (which already isolates `name` from `channel` during parsing) can. `PackageName::as_normalized()`'s case-folding matches how conda treats package names as case-insensitive for identity purposes, so `Pandas` and `pandas` compare equal, consistent with FR-004's own "bare name... matches" language implicitly using conda's own package-name identity rules, not raw byte-for-byte string comparison. `bare_name()` returns `Option<String>`: for a `PackageSpec` built via the validating `parse()`, `.name.as_exact()` is always `Some`, so the `Option` costs that caller nothing; for one built via `from_resolved_default`, "no bare name is extractable" is a real, possible state this ticket's own design introduces — one `PackageSpec::parse`'s own callers could never produce — and `Option` is the type that models it directly (Constitution V, Explicit Over Implicit), rather than relying on a sentinel value a reader has to trust "happens to never collide."

**Alternatives considered**: `PackageName::from_matchspec_str_unchecked` (cheaper — no full `MatchSpec` reparse) is rejected because it produces the wrong answer for a channel-qualified spec, as shown above — a correctness defect, not an efficiency tradeoff. Storing a parsed `rattler_conda_types::MatchSpec` alongside `PackageSpec`'s existing opaque `String` (avoiding any re-parsing at merge time) was considered and rejected as unjustified complexity (Constitution I) for a function called at most once per package per invocation — not a hot path.

## Decision: Additive, supersede-by-bare-name merge

**Decision**: `src/ephemeral/defaults.rs` is organized around one free function:

```rust
pub(crate) fn effective_packages(explicit: &[PackageSpec], defaults: &[PackageSpec]) -> Vec<PackageSpec>
```

Implementation: collect the set of `Some` bare names present in `explicit` (every per-invocation entry has one, by construction — see "Bare package name extraction," above); walk `defaults` in its own original order, keeping every entry whose `bare_name()` is `None` (nothing to compare it against, so it always survives) or whose `Some` bare name is not in that set; append every `explicit` entry, in its own original order, to the end. No enum distinguishes "explicit" from "default-or-override" — that distinction no longer drives any branching. CLI-package parsing (reject a syntactically invalid match-spec string, collapse "no packages named" to an empty `Vec`) is a plain free function, `parse_explicit_packages(packages: Vec<String>) -> Result<Vec<PackageSpec>, InvalidPackageSpec>` — named for what it parses (the CLI's own per-invocation package list): an empty `explicit` list and a non-empty one go through the exact same additive-merge code path (an empty `explicit` simply supersedes nothing and contributes nothing, which is already `effective_packages`'s natural, non-special-cased behavior for that input — no `if packages.is_empty()` branch needed anywhere in this function).

`effective_packages` never deduplicates entries *within* either `defaults` or `explicit` that happen to share a bare name with each other (as opposed to a `defaults` entry sharing a bare name with an `explicit` one, which *is* handled): the Resolved Default Package Set may itself contain two entries with the same bare name and different constraints, and both are preserved unchanged in the Effective Package Set, reaching the existing solver exactly as any other duplicate top-level request already would. FR-004's supersede rule is textually scoped to "the per-invocation package's bare name matches an entry in the resolved *default* package set" — a cross-list collision only; spec.md's own Assumptions section separately, explicitly scopes same-bare-name collisions *within* the per-invocation list to `allez oneshot`'s own existing solver path, not to this merge step. Extending that same non-scope symmetrically to the default list's own internal duplicates (rather than an asymmetric rule that treats the two lists differently) keeps `effective_packages`'s contract exactly as narrow as FR-002/FR-004 state it: FR-002 forbids `allez`-specific validation or special-casing on top of whatever `create_default_packages` resolves to, and silently collapsing two distinct entries the user's own `.condarc` names would be exactly that.

`create_ephemeral_environment`'s signature (`src/ephemeral/mod.rs`) becomes `(explicit: Vec<PackageSpec>, defaults: Vec<PackageSpec>, channels: ResolvedChannels)`: it calls `effective_packages(&explicit, &defaults)` itself, as its own first step, before any filesystem or network work begins. `oneshot.rs`'s own orchestration therefore calls `create_ephemeral_environment(explicit, defaults, channels)` directly, with no separate merge call of its own — `effective_packages` is invoked from exactly one call site (`create_ephemeral_environment`'s own body), not re-exported for `oneshot.rs` to call first. Bundling the merge inside the one public function this feature's callers already go through — rather than only inside the one CLI command that happens to call it today — makes FR-003/FR-004's additive/supersede guarantee available to any caller of `create_ephemeral_environment`, not conditional on that caller separately knowing to reach a `pub(crate)` merge helper it cannot even see from outside the crate.

**Rationale**: FR-003 ("per-invocation packages... MUST be added to the resolved default package set, not replace it") and FR-004 ("the per-invocation package MUST supersede that entry... rather than both being retained") describe a merge-by-name operation, not a "does an explicit list exist at all" branch. An enum distinguishing "explicit" from "default-or-override" would misdescribe this additive precedence (spec.md's Assumptions section names GEN-24 FR-005/FR-006 and User Story 3/Acceptance Scenario 3, and GEN-25 FR-001, as the mechanism and precedence FR-003/FR-004 define instead) — an enum variant meaning "use this list *instead of* the default" would be exactly the kind of implicit, surprising mismatch between a name and its behavior Constitution V (Explicit Over Implicit) warns against. Resolving the merge inside `create_ephemeral_environment` itself, rather than requiring every caller to pre-merge before calling it, keeps FR-003/FR-004's guarantee attached to the one function whose own contract already is spec.md's Key Entity definition of the Effective Package Set (install this top-level request, nothing more): any caller supplies its own explicit and default inputs and gets the same precedence applied identically, without needing to reimplement or even reach `effective_packages` itself — a plain two-list parameter pair, not an enum, still keeps that call free of any "replace-vs-default" branch for `create_ephemeral_environment` to misread.

**Alternatives considered**: An enum with a variant for each of "replace with this list" and "use the default" was rejected — the entire *reason* for such variants to exist (a replace-vs-default choice) is absent from FR-003/FR-004's additive precedence. Merging by exact match-spec string equality instead of bare name was rejected — directly contradicts FR-004's "regardless of which of the two carries a version or build constraint" clause. Splitting into two API calls (`create_ephemeral_environment` for an explicit-only request, plus a separate defaults-aware variant) — the shape GEN-24's own PR review raised against that ticket's `default_override` parameter — was considered and rejected: a caller with both an explicit list and a resolved default set (every real caller this ticket has) would still need to pick one call correctly and could not express "both, merged" through either alone; one function taking both lists directly removes that ambiguity instead.

## Decision: No built-in fallback package list of any kind

**Decision**: No constant, static list, or other `allez`-authored default package set exists in this design. When the resolved `create_default_packages` value is empty (unset, or explicitly configured empty) *and* no per-invocation packages are named, `effective_packages` returns an empty `Vec`, and `create_ephemeral_environment` must succeed on zero total packages, per FR-002/spec.md US1-AS2. A zero-package request reaching `create_ephemeral_environment`/`solve_packages` (`src/ephemeral/solve.rs`) needs direct test coverage at the `solve_packages` layer (Test strategy, below), rather than relying solely on the end-to-end CLI scenario (US1-AS2) to be the only signal that an empty top-level request actually solves and installs successfully.

**Rationale**: FR-002 is explicit: "`allez` MUST use whatever `create_default_packages` resolves to, including an empty list... with no `allez`-specific fallback, validation, or special-casing of its own on top of that resolution." A built-in fallback list would itself be exactly the kind of `allez`-specific special-casing FR-002 forbids — a second, redundant fallback layer sitting on top of a resolution FR-002 already defines completely, including its empty case. This differs deliberately from `channel_config`'s own unset-channels behavior (an absent/malformed `.condarc` falls back to `condarc::expand_channels(&Config::default())`, not an empty channel list): the two settings share `channel_config::document`'s resolution mechanics, but FR-002 itself only defines a no-fallback posture for `create_default_packages`; it says nothing about channels, whose own no-fallback-vs-fallback posture is GEN-23's separate, already-settled design, unchanged by this ticket. FR-002's "including an empty list" draws no distinction between "unset" and "configured to `[]`" — both resolve to the same empty list.

**Alternatives considered**: Keeping a built-in fallback list active only for the case where `create_default_packages` is entirely unset (as opposed to configured-empty) was considered and rejected — FR-002 draws no such distinction ("including an empty list" covers both "unset" and "configured to `[]`" identically, per spec.md's own Edge Cases section), and drawing one anyway would be `allez` inventing a fallback the setting itself was never asked to have.

## Decision: `create_default_packages` parsing correctness is inherited, not re-tested

**Decision**: This ticket's own test suite (§ Test strategy, below) never re-validates that `create_default_packages` itself parses the way real conda parses it — that correctness is already established, at the `condarc` crate level, by GEN-36's conformance harness (`tests/condarc_conformance.rs`). 31 of its `conformance/condarc/valid/*.json` / `conformance/condarc/expected/*.json` fixture pairs carry a `create_default_packages` key — they are generic `list_of_strings_*` battery fixtures that set several list-typed settings (`channels`, `default_channels`, `aggressive_update_packages`, `create_default_packages`, and others) simultaneously, not fixtures purpose-built for `create_default_packages` alone — each compared field-for-field (not merely accept/reject) against a real conda oracle's own resolved value, `create_default_packages` included. GEN-30's own tests exercise only *this ticket's own consumption* of an already-conformance-validated `Option<Vec<String>>` value: extracting it from a parsed `Config`, turning each entry into a `PackageSpec`, and merging it with the per-invocation list.

`allez`'s own `channel_config::document` module calls `condarc::parse()` with `ParseOptions::default()`, a pre-existing call-site choice this ticket does not change; `default_packages_config::create_default_packages_from_document`'s own `.unwrap_or_default()` (§ data-model.md) already normalizes every shape that resolution can hand it to the same empty `Vec` when the setting is absent, so no divergence in how `condarc::parse()` is invoked elsewhere in this codebase can produce a different outcome for this ticket's own logic.

**Rationale**: Constitution VIII (100% spec test coverage) requires every FR to have test coverage — not that this ticket re-derive coverage GEN-36 already owns at the `condarc` crate level. Re-running conformance testing against a real conda oracle for a field this ticket does not parse (parsing happens correctly before this ticket's code ever runs) would duplicate GEN-36's own test investment for no correctness benefit; this ticket's own tests need to prove something narrower and different — that its own extraction/merge logic behaves correctly given whatever already-conformant value `condarc::parse()` hands it.

**Alternatives considered**: Adding a new conformance-style test asserting `allez`'s own resolution matches real conda's `create_default_packages` behavior end-to-end (rather than relying on the crate-level harness) was considered and rejected as duplicating coverage that exists at the correct architectural layer (the `condarc` crate, which is the thing that actually parses YAML), for no additional correctness signal.

## Decision: `default_packages_config::create_default_packages_from_document` never rejects a resolved entry

**Decision**: `create_default_packages_from_document(document: &CondarcDocument) -> Vec<PackageSpec>` — no `Result`, cannot fail. Each string in the resolved `create_default_packages` list becomes a `PackageSpec` via a second, infallible constructor, `PackageSpec::from_resolved_default(input: String) -> PackageSpec` (`src/ephemeral/defaults.rs`), which stores the string opaquely with no `MatchSpec` parse at all — unlike `PackageSpec::parse`, `from_resolved_default` cannot return `Err`, and is used only for `create_default_packages`-sourced entries (never for CLI-supplied packages, which always go through the validating `PackageSpec::parse`). Whatever string `create_default_packages` resolves an entry to — including an empty string, or any other string `MatchSpec`'s strict parser would reject — becomes a `PackageSpec` here unchanged, without exception, and is handed to `effective_packages` (the merge, below) as a `defaults` entry unchanged. None is rejected at this extraction layer; whether a given entry then survives into the Effective Package Set is `effective_packages`'s own concern (FR-004's supersede rule), not this function's.

**Rationale**: FR-002 forbids `allez`-specific validation of any kind on top of `create_default_packages`'s own resolution — no carve-out, no structural exception, no case where `allez` decides a resolved entry doesn't count. The only way to honor that literally is for this function to never fail: whatever the setting resolves to is what reaches the merge, unfiltered by this function. A surviving entry that doesn't name a real installable package — whether because it's empty, whitespace-only, or a nonsense name — fails at the same place any other nonexistent per-invocation package name already fails: `solve_packages`'s own existing `MatchSpec::from_str` call (`src/ephemeral/solve.rs`), which runs once per package regardless of source and converts a parse or solve failure into `EphemeralEnvError::UnresolvablePackage`/`ResolutionFailed`. A default-sourced entry that survives the merge uses this same solve-time error path as any other package, later than an extraction-time check would have caught it, but through no `allez`-specific validation of its own. Never-rejecting also means a `create_default_packages` entry can carry arbitrary text, including control characters, further downstream than a CLI-supplied package name (which `PackageSpec::parse`'s `MatchSpec` validation would already have rejected): three of `allez`'s four existing rendering paths for a package string (`tracing`'s `Debug` formatting in lifecycle events and the oneshot-outcome event; `serde_json`'s default-JSON escaping) already handle arbitrary text safely; `--human` mode's `EphemeralEnvError::Display` path, reused verbatim from before this ticket, does not escape control characters when interpolating a package string — a pre-existing property of that rendering path, unrelated to and unchanged by this ticket, which this design does not make newly reachable by any means other than the same never-reject choice FR-002 itself requires.

**Alternatives considered**: Parsing each entry via the existing `PackageSpec::parse()` and failing immediately on a syntactically-invalid one was rejected — `PackageSpec::parse` is unsuitable here because it would reject a `create_default_packages`-resolved entry before solve time purely because `allez` decided that value isn't good enough, which is exactly the special-casing FR-002 forbids; the fact that it would fail with the same error *category* as the CLI case doesn't change that it fails *earlier*, for a reason FR-002 doesn't authorize. Introducing a distinct failure category for this case was rejected as not this ticket's scope to add a new contract surface. Silently dropping an unparseable entry was rejected — it would narrow the user's own real, intentional `.condarc` configuration without any signal, and FR-002's "use whatever it resolves to" doesn't distinguish "use" from "silently use less than."

## Decision: `skills/allez-oneshot.md` documentation content (FR-005)

**Decision**: Add a new `### Default packages` subsection inside the existing `## Usage` section, positioned immediately before its `### Examples` sibling subsection, stating plainly: (1) with no packages named before `--`, the environment gets exactly whatever the caller's own `~/.condarc` `create_default_packages` setting resolves to (linking to conda's own documented meaning of that setting, not restating it); (2) named packages are *added* to that resolved set; (3) a named package whose bare name matches a default-set entry replaces that one entry (version/build included) rather than both ending up installed. No code example changes: the existing `allez oneshot numpy pandas -- python script.py` example under `### Examples` remains accurate under this precedence rule without any wording change.

A new test, `skills_doc_states_default_package_source_and_precedence` (`tests/skills_doc.rs`, a new standalone test binary — this file's doc content has no existing test coverage to extend), reads `skills/allez-oneshot.md` and asserts its `### Default packages` subsection's text contains: a substring naming `create_default_packages` and `~/.condarc` together (source fact), and a substring stating both that named packages are added and that a matching bare name replaces the default entry (precedence fact). This is a substring/content assertion, not a full-prose match — it verifies the two required facts are present in the file, not the exact wording chosen for them.

**Rationale**: FR-005/spec.md's US2-AS3 require exactly this: an agent reading `skills/allez-oneshot.md` — the human-and-agent-facing reference FR-005 names for this documentation requirement — must be able to learn both facts (source of defaults, precedence) without reading source code. `skills/allez-oneshot.md` structures `## Usage` as the parent heading of `### Examples`; placing the new subsection as `### Default packages`, a sibling of `### Examples` positioned first, answers "what packages do I get if I name none, and what happens if I name one that collides" before a reader reaches the examples that rely on knowing that, without altering the file's own heading hierarchy. Constitution VIII (100% spec test coverage) requires every FR to have test coverage; a substring-content test gives FR-005 an automated, named assertion rather than relying solely on human review to catch a silent removal of either required fact.

**Alternatives considered**: A separate new top-level doc file was rejected — FR-005 explicitly names `skills/allez-oneshot.md` as the required location, and this project has no other user/agent-facing `allez oneshot` reference to split the explanation across. A new top-level `## ` section placed after `## Usage` was considered and rejected — `### Examples` is `## Usage`'s own child heading, not its sibling, so a new top-level section would sit outside that parent-child relationship rather than simply preceding `### Examples` within it; a `### `-level sibling keeps the file's existing two-level structure intact.

## Test strategy

**Fixture reuse, no new fixture package.** `tests/fixtures/ephemeral_channel/README.md` documents `fixture-default-alpha`/`fixture-default-beta` as "dependency-free, noarch root-channel packages meant for tests that need an explicit, fixture-resolvable package request" — exactly what this ticket's own precedence tests need, exercised via a test `.condarc`'s `create_default_packages:` key rather than only via explicit CLI package names. No fixture-generation script change. That README's "Default-package candidates" section states that no built-in default package list exists and that the zero-packages case succeeds with an empty installed set — tracked in `plan.md`'s Project Structure file list alongside the test changes below.

**Conformance scope**: see the "inherited, not re-tested" Decision above — no conformance-style test is added by this ticket; `create_default_packages`'s own parsing correctness against real conda is GEN-36's responsibility.

**Unit-level (`src/ephemeral/defaults.rs`)** — SC-004's three enumerated cases, plus five bare-name/intra-list edge cases, as direct `effective_packages()` unit tests: (a) no per-invocation packages ⇒ result equals `defaults` exactly, in order; (b) a per-invocation package sharing no bare name with `defaults` ⇒ result is `defaults` followed by every per-invocation package; (c) a per-invocation package's bare name matches a `defaults` entry, and the *default* entry carries the version/build constraint (e.g. `numpy=1.2` default vs. bare `numpy` per-invocation) ⇒ that one `defaults` entry is dropped, the per-invocation package's own (unconstrained) spec is retained, and no other `defaults` entry is affected; (c2) the same collision with the constraint on the *other* side — the *per-invocation* entry carries a build/version constraint and the colliding `defaults` entry is bare (e.g. bare `numpy` default vs. `numpy=2.0=py311h_0` per-invocation) ⇒ the default entry is still dropped and the per-invocation package's own constrained spec is retained, proving FR-004's "regardless of which of the two carries a version or build constraint" clause symmetrically, not only for the direction (c) exercises; (d) empty `defaults` and empty `explicit` ⇒ empty result (no built-in fallback, FR-002) — `effective_packages_empty_explicit_and_empty_defaults_returns_empty`; (e) a channel-qualified per-invocation spec (e.g. `conda-forge::numpy`) supersedes a bare `numpy` default entry — asserts `bare_name()` compares by name only, ignoring the channel qualifier on either side; (f) two `create_default_packages`-sourced entries sharing a bare name (e.g. `numpy=1.2`, `numpy=2.0`) with no colliding per-invocation entry ⇒ both survive in the result; (g) the same, but for two `explicit` entries; (h) per-invocation `Pandas` (differently cased) supersedes a default entry named `pandas` — asserts `bare_name()`'s case-folding comparison, not raw byte-for-byte string comparison.

**Integration-level (`src/ephemeral/solve.rs`)** — one new test, `solve_packages_empty_input_returns_no_records`: calls `solve_packages` directly against the checked-in local fixture channel with an empty `packages` slice, asserting `Ok` with an empty `records` list. No network access needed (the fixture channel is `file://`-local); this proves `Gateway::query`/`SolverTask` actually succeed on an empty request, not merely that `create_ephemeral_environment`'s own call-site logic reaches that point — at the cheapest layer capable of proving it, rather than relying solely on the heavier end-to-end CLI scenario (US1-AS2, below) as the only signal.

**Module-level (new `src/default_packages_config.rs`)** — against a directly-constructed `CondarcDocument` (no I/O, matching this module's own no-I/O contract): `CondarcDocument::Absent` and `CondarcDocument::FellBack(_)` both resolve `create_default_packages` to an empty `Vec` (FR-002's "no fallback... of its own"); a `CondarcDocument::Parsed` whose `create_default_packages` is `None` (key omitted) also resolves to empty (`create_default_packages_from_document_parsed_none_resolves_to_empty`); a `Parsed` document with a populated list passes every entry through unchanged, each becoming a `PackageSpec` via `from_resolved_default` — this holds identically whether an entry is a well-formed match-spec, an empty string (`create_default_packages_from_document_empty_string_entry_resolves_successfully`), a whitespace-only string (`create_default_packages_from_document_whitespace_only_entry_resolves_successfully`, exercising `bare_name()`'s own fallback-path unit test below), or any other arbitrary already-resolved string (`create_default_packages_from_document_arbitrary_string_entry_resolves_successfully`) — none of these shapes is rejected here (locks in the "never rejects a resolved entry" Decision above).

**Unit-level (`src/ephemeral/defaults.rs`, `bare_name()`)** — one new test alongside the SC-004 cases above: `bare_name_of_an_unparseable_resolved_default_spec_returns_none` — constructs a `PackageSpec::from_resolved_default(String::new())` directly and asserts `bare_name()` returns `None` (not `Some("")`), locking in that this is reachable, deliberate behavior for default-sourced entries, not dead code.

**Module-level (`src/channel_config/document.rs`)** — `read_condarc`/fallback-classification tests against real temp-file fixtures, at parity with `channel_config`'s existing coverage of the same logic, returning `CondarcDocument` in place of `ChannelConfigResolution`: `resolve_document_from_missing_path_resolves_to_absent` (no file at the given path ⇒ `Absent`, silent, no event); `resolve_document_from_unreadable_file_falls_back_and_emits_event` (a file containing invalid-UTF-8 bytes ⇒ `FellBack(FallbackReason::Unreadable)`, one `emit_fallback` call — the exact technique `channel_config`'s own existing `invalid_utf8_emits_one_unreadable_fallback_event` test already uses, portable across every platform with no `#[cfg(unix)]` gate and no dependence on the invoking user's own OS permissions, unlike a chmod-based approach that a privileged/root test-runner account could read regardless); `resolve_document_from_malformed_yaml_falls_back_and_emits_event` (a file `condarc::parse()` rejects ⇒ `FellBack(FallbackReason::Rejected)`, one `emit_fallback` call); `resolve_document_from_valid_file_returns_parsed` (a well-formed `.condarc` ⇒ `Parsed(config)` with the expected fields); `consecutive_calls_read_changed_contents_without_caching` (two calls against a path whose contents changed between them return two different results — no caching). Project-local-`.condarc`-exclusion coverage (below) lives at the end-to-end layer instead of here: proving it in-process would require mutating this test binary's own working directory and `ALLEZ_CONDARC_PATH`, and `serial_test::serial` only excludes other `#[serial]`-marked tests in the same binary — it does not stop an unmarked test on another thread from observing either mutation, so an in-process version of this test is not actually safe to run in parallel with the rest of this module's own suite.

**End-to-end (`tests/oneshot_exec.rs`)** — new scenarios, each a fixture `.condarc` with a `channels:` entry plus a `create_default_packages:` entry naming one or more fixture packages:

- US1-AS1: `create_default_packages: [fixture-default-alpha]`, zero per-invocation packages ⇒ installed set is exactly `{fixture-default-alpha}`.
- US1-AS2: no `create_default_packages` key at all, zero per-invocation packages ⇒ environment creation succeeds with an empty installed set, proving FR-002's "no fallback" requirement directly — the `solve_packages`-layer test above already establishes the solver itself accepts zero specs; this scenario proves the same holds through the full CLI path.
- US2-AS1: `create_default_packages: [fixture-default-alpha]`, per-invocation `fixture-probe` (no shared bare name) ⇒ installed set is `{fixture-default-alpha, fixture-probe}`.
- US2-AS2: `create_default_packages: [fixture-default-alpha=9.9.9]` (a version that does not exist in the fixture channel — on its own, unresolvable), per-invocation `fixture-default-alpha` (unconstrained — resolvable to the fixture's real `1.0.0`) ⇒ the invocation **succeeds**, installing `fixture-default-alpha` `1.0.0`. This is the actual proof of supersede-not-duplicate: if the default entry survived alongside the per-invocation one, the solve would fail (no version satisfies both an unconstrained request and a request pinned to a nonexistent `9.9.9`); success is only possible if the default entry was dropped. This scenario proves the full `oneshot.rs` → `create_ephemeral_environment` (merge-then-install) path is wired correctly end-to-end — see "Merge coverage layers," below, for the direct `create_ephemeral_environment`-layer test that also exercises this same collision.
- Project-local `.condarc` exclusion (spec.md Edge Cases): `OneshotHarness::command()` already sets `ALLEZ_CONDARC_PATH`/`ALLEZ_EPHEMERAL_ROOT` via per-invocation `Command::env(...)` rather than a process-wide `std::env::set_var` — `OneshotHarness`'s own struct-level doc comment states this is precisely so tests "run safely in parallel." This new scenario extends that same harness with `.current_dir(...)` pointed at a dedicated temporary directory holding its own distinct, decoy `.condarc` (with a `create_default_packages:` entry naming a fixture package the real test `.condarc` never names); the subprocess's `ALLEZ_CONDARC_PATH` still points at the harness's own real test `.condarc`. Asserts the resolved default package set reflects only the real test `.condarc`, never the decoy in the subprocess's own working directory. Subprocess-scoped environment and working-directory control (assert_cmd's own per-command builder) needs no `serial_test`/RAII guard/shared mutable process state at all — the property is proven in a fresh child process the test harness never has to synchronize against.

Under FR-002, empty explicit packages plus an empty resolved default set succeeds with zero installed packages — an outcome US1-AS2 above covers end-to-end; no test at any layer asserts a failure for that input.

**Merge coverage layers** — `create_ephemeral_environment` calls `effective_packages(&explicit, &defaults)` itself as its own first step (see "Additive, supersede-by-bare-name merge," above), so it takes the `(explicit, defaults)` pair directly rather than an already-merged list computed by its caller. Merge coverage therefore spans three layers, each proving something the others don't: the direct `effective_packages` unit tests above (the algorithm itself, isolated from any I/O); one new `tests/support/defaults.rs` test, `create_ephemeral_environment_supersedes_matching_default_entry_by_bare_name` (the same file whose own three replace-only-precedence tests this ticket removes, now holding the one test that actually proves additive/supersede precedence at this layer), calling `create_ephemeral_environment` directly with a colliding `(explicit, defaults)` pair against the fixture channel and asserting the installed set reflects supersede-not-duplicate (proving the merge is actually wired into the function's own body, not merely available to call separately); and the US2-AS2 end-to-end scenario, which exercises the full `oneshot.rs` → `create_ephemeral_environment` path in one invocation including CLI parsing and `.condarc` resolution. None of the three is redundant with the others (Constitution IV; test-proportionality): the unit tests prove the algorithm, the `tests/support/defaults.rs` test proves the wiring, and the end-to-end scenario proves the full invocation.

**No new Cargo feature, dependency, or fixture asset.** Every new/changed test above runs under the existing `test-config-override` feature (end-to-end) or as a plain unit test (module-level); nothing here needs network access, so `network-tests`/`conformance-tests` are unaffected.
